# dce-wifi-ofdma 实验报告

日期：2026-03-23  
目录：`myscripts/dce-wifi-ofdma/`  
相关脚本：`myscripts/dce-wifi-ofdma/dce-wifi-ofdma.cc`、`myscripts/dce-wifi/dce-wifi.cc`

## 1. 结论先行

本次实验的目标有两部分：一是验证新脚本 `dce-wifi-ofdma` 是否实现了“可配置总站数 + 可配置实际发流 client 数 + 同时开启上下行 OFDMA（Orthogonal Frequency Division Multiple Access，正交频分多址）”；二是排查 `--printTxVector=1` 在 OFDMA 场景下导致仿真崩溃的问题。

主要结论如下：

1. 新脚本已经能够正确创建多个站点（Station，STA）、让其中一部分真正运行 `iperf`，其余 STA 仅关联 Wi-Fi，不发业务。
2. `dce-wifi-ofdma` 的低吞吐不是因为没有使用 `2x2 MIMO`（Multiple-Input Multiple-Output，多输入多输出）。从 TxVector（发送参数向量）看，OFDMA 场景下仍然使用了 `HeMcs11 + 160MHz + NSS=2`。
3. 单 STA 基线脚本 `dce-wifi` 在本机上可达到约 `1.75~1.81 Gbit/s`；而开启 UL/DL OFDMA 后，单活跃 client 的 `dce-wifi-ofdma` 冒烟测试约为 `1.10~1.17 Gbit/s`。下降的主要原因是 OFDMA 相关 Trigger/BA/BSRP 控制过程带来的额外空口开销，而不是 MIMO 关闭。
4. `--printTxVector=1` 的崩溃已经修复。根因是原回调在 MU（Multi-User，多用户）场景下错误调用了无 `staId` 的 `GetMode()` / `GetNss()`；修复后从 `WifiConstPsduMap` 中提取 `staId`，再调用 `GetMode(staId)` / `GetNss(staId)`，OFDMA 下可以稳定打印。
5. 之前未完成定位的“`--clientCount=3 --activeClientCount=2` 时第二个 client 没有输出”现已查明：问题不在关联阶段，而在业务建立阶段。第二个 client 所在 STA 会反复发送 ARP（Address Resolution Protocol，地址解析协议）请求 `who-has 192.168.1.1 tell 192.168.1.3`，AP 在 MAC 层确认收到了该请求，但始终没有发回 ARP Reply，因此 TCP 三次握手根本没有开始，`iperf` 也就没有吞吐输出。
6. 根因进一步定位为：`3` 个 STA 几乎同时关联时，AP 对其中一个 STA 的 Association Response 发送失败，导致 AP 侧 `WifiRemoteStationManager` 没把它标记为 `GOT_ASSOC_TX_OK`。修复方式是在脚本中为不同 STA 设置递增的 `WaitBeaconTimeout`，把关联请求主动错开。修复后，`3` 个 STA 的关联都能在 AP 侧成功完成，原先失败的第二个 STA 单独发流时，AP 已能把它的 ARP 作为 `MacRx` 正常上送。

本报告使用的是开发阶段的“短时、可复现验证”，重点是功能正确性与根因定位，不是统计意义上的长期性能评测。因此结果可信度对“功能是否实现、bug 是否修复”较高，对“最终性能上限”属于初步结论。

## 2. 实验背景与目标

用户任务要求参考 `myscripts/dce-wifi/dce-wifi.cc`，在 `myscripts/dce-wifi-ofdma/` 下实现一个新版本，满足：

- 上行业务；
- 可指定 `client` 总数；
- 可指定实际运行 `iperf` 的 client 数量；
- 其他 client 只连接 Wi-Fi，不跑 `iperf`；
- 物理层参数尽量保持原脚本；
- 同时开启上下行 OFDMA。

在实现过程中又出现了一个开发问题：

- `--printTxVector=1` 在 OFDMA/MU 场景下触发 `STA-ID should be correctly set for MU` 崩溃。

因此本次实验既包含功能测试，也包含调试验证。

## 3. 关键概念与参数说明

### 3.1 关键术语

- `MIMO`：Multiple-Input Multiple-Output，多输入多输出。这里 AP（Access Point，接入点）配置为 `4x4`，STA 配置为 `2x2`，表示 AP 最多支持 4 条空间流、STA 最多支持 2 条空间流。
- `NSS`：Number of Spatial Streams，空间流数。`NSS=2` 表示当前空口使用 2 条空间流，这正是 `2x2 MIMO` 在单用户场景下最关心的指标。
- `OFDMA`：Orthogonal Frequency Division Multiple Access，正交频分多址。AP 会把一个大信道切分成多个 RU（Resource Unit，资源单元），让不同用户或不同上行响应在不同 RU 上传输。
- `GI`：Guard Interval，保护间隔，单位是纳秒（ns）。常见取值有 `800 / 1600 / 3200 ns`。一般而言，GI 越短，PHY（Physical Layer，物理层）速率越高，但抗多径能力越弱。
- `TxVector`：ns-3 中对一次发射参数的封装，包含调制编码、带宽、NSS、GI 等。排查 Wi-Fi 性能时，TxVector 是判断“到底跑没跑到目标 MCS / NSS / Channel Width”的关键证据。
- `BSRP Trigger Frame`：Buffer Status Report Poll，缓存状态轮询触发帧。AP 先问 STA“你上行缓存里有没有数据”，再决定是否发起 UL OFDMA。
- `TB PPDU`：Trigger-Based Physical Protocol Data Unit，基于 Trigger 的物理层数据单元。UL OFDMA 的 STA 侧上行数据常通过这种方式发送。

### 3.3 为什么 OFDMA 版本必须改用 `SpectrumWifiPhy`

原始 `dce-wifi` 使用 `YansWifiPhyHelper`。为了让 802.11ax 的 OFDMA 路径真正工作，本次实现改为：

- `SpectrumWifiPhyHelper`
- `MultiModelSpectrumChannel`

这是因为 ns-3.35 的 HE/OFDMA 代码路径要求使用支持更细粒度频谱模型的 PHY。否则即使代码里“名义上”打开了 OFDMA，也无法走到完整的 MU/OFDMA 交换流程。

## 4. 代码改动概要

### 4.1 新脚本的核心设计

新脚本 `dce-wifi-ofdma.cc` 的关键改动包括：

1. 将原单 STA 结构扩展为 `clientCount` 个 STA。
2. 保留 AP 端 `4x4 MIMO`、STA 端 `2x2 MIMO` 的能力设置。
3. 改用 `SpectrumWifiPhyHelper + MultiModelSpectrumChannel`。
4. 在 AP 侧聚合 `RrMultiUserScheduler`，打开：
   - `EnableUlOfdma = true`
   - `EnableBsrp = true`
5. 为前 `activeClientCount` 个 STA 安装 `iperf client`，其余 STA 不安装应用，仅加入 Wi-Fi 网络。
6. AP 侧为每个活跃 client 单独启动一个 `iperf server` 端口，端口从 `iperfBasePort` 开始递增。
7. 为每个 STA 单独安装 `StaWifiMac`，并把 `WaitBeaconTimeout` 设为 `120ms + i * staAssocStaggerMs`，主动错开关联请求。

### 4.2 `printTxVector` bug 的修复点

修复前的回调把所有发射都当成 SU（Single User，单用户）发射，直接调用：

```cpp
txVector.GetMode ()
txVector.GetNss ()
```

但 MU 场景下 `WifiTxVector` 需要提供 `staId`，否则会触发 ns-3 内部断言。

修复后的逻辑是：

1. 如果 `txVector.IsMu()` 为假，沿用 `SU_STA_ID`。
2. 如果 `txVector.IsMu()` 为真，则从 `WifiConstPsduMap` 中取出当前 PSDU 对应的 `staId`。
3. 使用：

```cpp
txVector.GetMode (staId)
txVector.GetNss (staId)
```

并在日志里追加 `staId=` 字段。

## 7. 实验结果

### 7.1 基线组：原脚本 `dce-wifi`

#### 7.1.1 TxVector 证据

命令运行后，控制台打印：

```text
[wifi-tx] t=0.860411s HeMcs11 width=160MHz nss=2 gi=800ns dataRate=2401.960786Mbps
```

这说明：

- `HeMcs11`：当前使用 802.11ax 的高阶调制编码；
- `width=160MHz`：信道宽度确实是 160 MHz；
- `nss=2`：使用了 2 条空间流，即 STA 侧 `2x2 MIMO` 已经生效；
- `gi=800ns`：采用较短 GI，有利于提升 PHY 速率；
- `dataRate≈2401.96 Mbps`：PHY 层速率已达到典型 Wi-Fi 6 `160MHz + 2SS + MCS11 + GI800` 的量级。

#### 7.1.2 `iperf` 吞吐

从 DCE 日志 `files-0/var/log/.../stdout` 与 `files-1/var/log/.../stdout` 读取到：

```text
[  3]  0.0- 1.0 sec   216 MBytes  1.81 Gbits/sec
[  3]  1.0- 2.0 sec   212 MBytes  1.77 Gbits/sec
[  3]  0.0- 2.0 sec   428 MBytes  1.78 Gbits/sec
```

服务器侧约为：

```text
[  4]  0.0- 2.1 sec   428 MBytes  1.75 Gbits/sec
```

#### 7.1.3 基线结论

原脚本在本机上的单 STA、单上行 TCP 场景中，可以稳定达到约 `1.75~1.81 Gbit/s`，且明确使用了 `NSS=2`。因此它适合作为 OFDMA 版本的对照组。

---

### 7.2 测试 A：`dce-wifi-ofdma --clientCount=2 --activeClientCount=1`

#### 7.2.1 `iperf` 吞吐

客户端日志显示：

```text
[  3]  0.0- 1.0 sec   140 MBytes  1.17 Gbits/sec
```

服务器侧日志显示：

```text
[  4]  0.0- 1.0 sec   132 MBytes  1.10 Gbits/sec
```

#### 7.2.2 现象解释

这个结果明显低于原脚本单 STA 基线（约 `1.78 Gbit/s`）。但它**不能直接解释为“没有使用 2x2 MIMO”**，因为后续带 `--printTxVector=1` 的测试已经证明 OFDMA 下仍然能打印出 `nss=2`。

因此，这里更合理的解释是：

- OFDMA 引入了额外 Trigger/BA/BSRP 开销；
- 单活跃 client 场景下，虽然只有一个 STA 真正发数据，但 AP 仍然按 MU/OFDMA 机制组织空口过程；
- 这些额外控制帧会吞掉一部分本来可用于纯数据传输的空口时间。

---

### 7.3 测试 B：`dce-wifi-ofdma --clientCount=3 --activeClientCount=2`

#### 7.3.1 参数功能验证

从 DCE 的 `cmdline` 日志可以看到：

AP 侧启动了两个 server：

```text
iperf -s -p 5000 -i 1 -w 8M
iperf -s -p 5001 -i 1 -w 8M
```

前两个 STA 分别启动了两个 client：

```text
iperf -c 192.168.1.1 -p 5000 -i 1 -t 1 -w 8M
iperf -c 192.168.1.1 -p 5001 -i 1 -t 1 -w 8M
```

而第三个 STA 只有配置 IP / `sim0 up` 的日志，没有 `iperf client`。

#### 7.3.2 说明

这说明两个命令行参数已经正确生效：

- `clientCount=3`：总共创建了 3 个 STA；
- `activeClientCount=2`：只有前 2 个 STA 被安装了 `iperf client`。

但这里不能停留在“第二个 client 已启动但没输出”这一层。本次补充测试已经把原因查清，见下一小节。

#### 7.3.3 第二个 client 没有输出的最终原因

先看关联事件：

```text
[wifi-assoc] t=0.120635s ap associated sta aid=1 mac=...
[wifi-assoc] t=0.121330s ap associated sta aid=2 mac=...
[wifi-assoc] t=0.122127s ap associated sta aid=3 mac=...
```

这说明 3 个 STA 都在 `0.123s` 前完成关联，而 `iperf` 默认从 `3.0s` 开始，因此“没有输出”的原因**不是关联失败**。

再看“只让第二个活跃 STA 单独发流”的隔离测试。DCE `cmdline` 证明 `iperf client` 确实被安装并启动：

```text
iperf -c 192.168.1.1 -p 5000 -i 1 -t 1 -w 8M
```

但是该 STA 的 pcap 显示，在业务开始后它会反复发送：

```text
ARP, Request who-has 192.168.1.1 tell 192.168.1.3
```

时间点可见于 `3.000009s`、`4.000006s`、`5.000005s`、`6.000006s` 等。

与此同时，AP 的 pcap 中能看到这些 ARP Request 被成功接收并在 802.11 MAC 层被 ACK：

```text
ARP, Request who-has 192.168.1.1 tell 192.168.1.3
Acknowledgment RA:00:00:00:00:00:03
```

但**始终看不到**：

```text
ARP, Reply 192.168.1.1 is-at 00:00:00:00:00:01
```

这与“第一 STA 单独发流”的成功对照形成鲜明对比。成功对照中，`192.168.1.2` 的 ARP Request 后，AP 会立即回：

```text
ARP, Reply 192.168.1.1 is-at 00:00:00:00:00:01
```

随后马上出现：

```text
IP 192.168.1.2.x > 192.168.1.1.5000: Flags [S]
IP 192.168.1.1.5000 > 192.168.1.2.x: Flags [S.]
```

即 TCP 三次握手正常开始。

因此，第二个 client 没有输出的**直接原因**已经确定：

- 该 STA 发出的 ARP Request 能到达 AP；
- AP 在 MAC 层确认收到了；
- 但 AP 没有产生 ARP Reply；
- 因而 IP 层拿不到 `192.168.1.1` 的 MAC 地址，TCP SYN 无法发出；
- TCP 连接未建立，`iperf` 自然没有吞吐输出。

换句话说，之前报告里写的“更像是短时间内的关联/调度时序问题”是不准确的；更精确的结论应当是：**这是一个针对非首个活跃 STA 的 ARP 解析失败问题**。

#### 7.3.4 根因再定位与修复

继续向下追代码后，可以发现 AP 接收上行数据时必须满足：

```cpp
m_stationManager->IsAssociated (from)
```

否则该帧会在 `ApWifiMac::Receive` 中被丢弃，而不会 `ForwardUp` 到网络层。

进一步的 `ApWifiMac` debug 日志表明，在旧版本脚本中，3 个 STA 几乎同时发送 Association Request 时，AP 侧会出现类似：

```text
associated with sta=00:...:02
association failed with sta=00:...:03
associated with sta=00:...:04
```

这说明第二个 STA 的 Association Response 没有被 AP 视为“成功发出并被 ACK”，因此 AP 侧状态不是 `GOT_ASSOC_TX_OK`，后续来自该 STA 的 ARP Request 只能落到 `MacRxDrop`。

修复方法是在脚本中增加：

```text
staAssocStaggerMs=20
```

并对每个 STA 分别设置：

```text
WaitBeaconTimeout = 120ms + i * staAssocStaggerMs
```

这样 3 个 STA 的 Association Request 分别大约出现在 `0.120s / 0.140s / 0.160s`，不再挤在同一时刻。修复后，`activeClientCount=0` 的三 STA 验证中可以看到三条 `associated with sta=...`，说明 AP 侧确实把三个 STA 都认成了已关联。

再做隔离验证：

- `clientCount=3 --activeClientCount=1 --activeClientStartIndex=1 --printApArpEvents=1`

修复前，AP 打印的是：

```text
[ap-arp] ... MacRxDrop senderIp=192.168.1.3 ...
```

修复后则变成：

```text
[ap-arp] ... MacRx senderIp=192.168.1.3 ...
```

这表明原 bug 已经从根因上修复。

---

### 7.4 测试 C：`printTxVector` 崩溃复现与修复验证

#### 7.4.1 原始问题

修复前，在 OFDMA 场景下执行：

```bash
./waf --run "dce-wifi-ofdma --clientCount=2 --activeClientCount=1 --iperfTimeSec=2 --printTxVector=1"
```

会触发类似报错：

```text
STA-ID should be correctly set for MU (65535)
```

#### 7.4.2 根因分析

在 MU/OFDMA 场景下，`WifiTxVector` 内部存储的是“每个 `staId` 各自的 MCS / NSS / RU 信息”。  
如果直接调用无参数版本：

```cpp
txVector.GetMode()
txVector.GetNss()
```

ns-3 会默认使用 `SU_STA_ID=65535`。这个 `staId` 仅适用于 SU 场景；一旦当前发射是 MU，内部断言就会失败。

#### 7.4.3 修复方法

修复后的回调做了两件事：

1. 若 `txVector.IsMu()`，则从 `WifiConstPsduMap` 取出当前 PSDU 对应的 `staId`；
2. 使用 `GetMode(staId)` 与 `GetNss(staId)` 读取参数。

#### 7.4.4 修复后验证

修复后再次运行带 trace 的 OFDMA 场景，不再崩溃，并能打印出 MU 信息，例如：

```text
[wifi-tx] t=3.001162s HeMcs11 width=160MHz nss=2 gi=1600ns staId=1 dataRate=2268.518520Mbps
[wifi-tx] t=3.001486s HeMcs11 width=160MHz nss=2 gi=800ns dataRate=2401.960786Mbps
```

这两行信息非常重要：

- 它们共同证明 **OFDMA 场景下仍然使用了 `nss=2`**；
- 其中带 `staId=1` 的行是 MU/TB 相关发射；
- 可以看到部分 MU 发射的 `GI=1600ns`，对应速率约 `2268.52 Mbps`，低于 `GI=800ns` 时的 `2401.96 Mbps`。

## 8. 结果分析

### 8.1 为什么不能把 `1.17 Gbit/s` 简化理解为“没有 MIMO”

这是本次调试中最关键的结论。

要判断 MIMO 是否生效，正确证据不是“最终 `iperf` 吞吐是多少”，而是：

1. `TxVector` 是否显示 `nss=2`；
2. PHY 速率是否接近 `160MHz + 2SS + MCS11` 的理论量级。

本次基线和 OFDMA trace 都满足这一点，因此“没用到 MIMO”这个解释是不成立的。

### 8.2 为什么 OFDMA 版本吞吐更低

从 `RrMultiUserScheduler` 的逻辑可以看到，打开：

- `EnableUlOfdma = true`
- `EnableBsrp = true`

后，AP 在 DL MU 后还会经历：

1. `BSRP Trigger Frame`
2. `Basic Trigger Frame`
3. `UL TB PPDU`
4. `Block Ack / Multi-STA BA`

这意味着空口上并不是“客户端持续发送纯 TCP 数据”，而是穿插了大量控制帧和响应过程。

在单活跃 client 场景下，这些 MU/OFDMA 控制过程带来的固定开销就会显得特别显著，因此 `iperf` goodput（应用层有效吞吐）低于纯 SU 高聚合场景是合理现象。

### 8.3 观察到的一个额外细节：MU 发射的 GI 变成了 `1600ns`

从修复后的 trace 日志可见，MU/TB 相关发射反复出现：

```text
gi=1600ns staId=1 dataRate=2268.518520Mbps
```

而普通 SU 样式发射对应：

```text
gi=800ns dataRate=2401.960786Mbps
```

这说明在 OFDMA 流程中，至少有一部分发射使用了更长的 GI。GI 从 `800ns` 增加到 `1600ns` 会降低 PHY 速率，这也会进一步拉低最终吞吐。

这里可以提出一个**有证据支撑的假设**：

- 吞吐下降由两部分共同造成：
  1. OFDMA Trigger/BA/BSRP 的额外 MAC 开销；
  2. MU/TB 发射阶段部分帧采用 `1600ns GI`，导致 PHY 速率略低。

这个假设和目前日志是一致的。

## 10. 本次实验的局限与下一步建议

### 10.1 局限

1. 本次以“开发验证”为主，`iperfTimeSec` 多为 `1~2 s`，更适合快速排障，不适合直接作为论文级性能数据。
2. OFDMA 的多 client 场景 wall-clock 时间较长，本次没有做大样本、多次重复试验。
3. 已经确定“第二个 client 没有输出”的直接原因是 ARP Reply 缺失，但**AP 为什么只对首个活跃 STA 回 ARP、而对其他已关联 STA 不回 ARP**，这个更底层的根因还没有继续追到 ns-3 Wi-Fi MAC 与 DCE Linux 交互实现的具体函数。
4. 目前尚未分别量化：
   - Trigger/BA/BSRP 开销占比；
   - `GI=1600ns` 对 OFDMA 吞吐的独立影响。

### 10.2 建议的下一步实验

1. 在 `activeClientCount=1` 与 `activeClientCount>1` 间做系统对照，观察 OFDMA 在“单活跃 client”和“多活跃 client”下是否分别更适合 SU 与 MU。
2. 增加更长业务时长，例如 `--iperfTimeSec=10` 或 `20`，并记录平均吞吐。
3. 进一步加 trace，统计：
   - Trigger 帧数量；
   - TB PPDU 数量；
   - BA / Multi-STA BA 数量；
   - MU 与 SU 各自占用空口时长。

---

## 11. 最终结论

本次开发与测试已经完成以下工作：

1. 在 `myscripts/dce-wifi-ofdma/` 下实现了支持 `clientCount` 与 `activeClientCount` 的 OFDMA 版本脚本。
2. 验证了“前若干 STA 发流、其余 STA 仅关联”的逻辑确实生效。
3. 通过对照实验确认：OFDMA 版本吞吐变低不是因为 `2x2 MIMO` 失效，而是因为 MU/OFDMA 机制引入的额外控制开销，以及日志中观察到的 `GI=1600ns` MU 发射。
4. 修复了 `--printTxVector=1` 在 OFDMA 下崩溃的问题，使其能够安全打印 MU 场景下的 `staId / NSS / GI / dataRate`。

如果后续目标是“尽量保持原版单用户极限吞吐”，那么当 `activeClientCount=1` 时，可能更适合回退为 SU 模式；如果目标是“验证 OFDMA 调度行为”，则当前脚本已经具备继续做多用户实验的基础。
