# 本地 `nr` 模块的 5G NR 能力支持情况

## 1. 结论先看

我检查的是当前本地 `../ns-3.35/contrib/nr` 这份代码，版本大致是：

- 分支：`5g-lena-v1.2.y`
- 提交：`fe0a1d2a`
- `git describe`：`v1.2-1-gfe0a1d2a`

这份本地 `nr` 模块可以看成“**基于 LTE 上层 + NR PHY/MAC 的 5G-LENA v1.2 系统级仿真器**”，适合做：

- NR PHY/MAC 层时频资源调度
- numerology / BWP / TDD-FDD / 波束赋形 / HARQ / AMC / QoS 类业务分流
- 端到端 EPC 场景仿真

但它**不是一个完整的 5G SA/5GC 仿真器**，也**不支持真正的 NR 空间复用 MIMO**。

你最关心的 4 个点，可以先直接看这个表：

| 能力 | 结论 | 说明 |
| --- | --- | --- |
| MU-MIMO | **不支持** | 文档明确把 `spatial multiplexing` 列为缺失项；源码里也把传输模式基本固定在 `SISO`。 |
| SU-MIMO | **不支持** | 有天线阵列和 beamforming，但没有真正的单用户多层空间复用。更准确地说是“**支持阵列/波束，不支持空间复用**”。 |
| 5QI | **部分支持** | 不是原生 5G `QoS Flow + SDAP + 5QI` 建模，而是借用 LTE 的 `EpsBearer::Qci`，但该枚举已更新到 Release 15，包含一批标准化 5QI/QCI 数值。 |
| 网络切片 | **部分支持** | 支持基于 `QCI/业务类型 -> BWP` 的**静态流量分流**，可近似做 `RAN slicing`；但不支持 5GC/SDAP/S-NSSAI 级别的真实网络切片。 |

---

## 2. 明确支持的能力

以下能力在本地文档、示例或源码里都能明确找到实现依据。

### 2.1 NR PHY/MAC 基础框架

- 面向 **3GPP Release-15 NR** 的 PHY/MAC 能力实现。
- 仍然复用 LTE 的高层和核心网，因此整体是 **NSA（non-standalone）** 结构，而不是 SA。

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:28`

### 2.2 Numerology

- 支持 numerology `0..5`，对应 SCS：
  - `15 / 30 / 60 / 120 / 240 / 480 kHz`
- 按 slot / symbol 粒度建模时序。

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:129`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:159`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:176`

### 2.3 BWP、多 numerology 频分复用、CA 近似能力

- 支持把频谱切成多个 **BWP**。
- 不同 BWP 可有不同 PHY/MAC 配置，例如 numerology、scheduler 等。
- 支持用不同 BWP 承载不同业务流。
- 支持 FDM of numerologies。
- 支持把 BWP 当作正交的 carrier / spectrum part 使用，能做一定程度的 CA / 分流建模。

注意：

- 这里的 BWP 不是严格等价于 3GPP UE 侧动态 active BWP 定义；
- 本地实现要求 BWP **频域上正交且不重叠**。

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:69`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:73`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:77`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:185`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:2004`

### 2.4 TDD / FDD

- 支持 **TDD**。
- 支持 **Flexible slot**，即 DL/UL 可在同一 flexible slot 中动态分配，属于 **dynamic TDD**。
- 支持 **FDD**，实现方式是“成对 BWP”。

限制：

- FDD 配对仅支持 **相同 numerology** 的 BWP。

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:200`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:207`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:216`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:218`

### 2.5 Beamforming / 阵列天线

- 支持阵列天线与波束赋形。
- 支持 **Ideal beamforming** 和 **Realistic beamforming**。
- Ideal beamforming 支持：
  - `CellScanBeamforming`
  - `DirectPathBeamforming`
  - `DirectPathQuasiOmniBeamforming`
  - `CellScanQuasiOmniBeamforming`
  - `QuasiOmniDirectPathBeamforming`
- Realistic beamforming 依赖 **SRS** 测量。

这说明你的 `nr-dce.cc` 里设置 `NumRows/NumColumns`、`ThreeGppAntennaModel`、`DirectPathBeamforming` 是有效的，但它提升的是**阵列增益/波束方向性**，不是空间复用层数。

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:434`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:482`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:519`

### 2.6 SRS

- 支持 **SRS transmission and reception**。
- 支持 **scheduler-based SRS**。
- 支持动态调整 SRS periodicity / offset。

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:590`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:617`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:624`

### 2.7 调度器

- 支持 **DL TDMA**。
- 支持 **DL OFDMA**。
- 支持 `RR / PF / MR` 等调度策略。
- UL 方向支持 **TDMA with variable TTI**。

限制：

- DL OFDMA 带有 **single-beam capability** 约束；
- 文档明确写了 **UL 只支持 TDMA**，不是 UL OFDMA。

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:1088`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:1090`

### 2.8 HARQ / AMC / CQI / 256-QAM

- 支持 **HARQ-CC** 和 **HARQ-IR**。
- 支持 CQI 驱动的 AMC。
- 文档写明支持最高到 **256-QAM**。
- 你的本地代码里如果使用 `NrEesmCcT2` / `NrEesmIrT2` 一类 error model，就能走到更高 MCS table。

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:28`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:1020`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:1300`

### 2.9 Uplink Power Control

- 支持 `NrUePowerControl`。
- 支持 **PUSCH / PUCCH / SRS power control**。
- 支持 **open loop** 和 **closed loop**。
- 同时支持 LTE 和 NR 两套 ULPC 公式。

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:686`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:701`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:708`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:714`

### 2.10 3GPP 信道、天线、REM、notching

- 支持 3GPP channel / propagation / antenna 相关系统级建模。
- 支持 REM（`NrRadioEnvironmentMapHelper`）。
- 支持 **notching / UFA**。

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:261`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:391`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:1347`

### 2.11 非授权频段相关抽象

- 支持 `UnlicensedMode`。
- PHY 有 `CCA_BUSY` 状态。
- UE 侧源码中存在 LBT 调度逻辑。

这说明本地代码对非授权场景不是完全空白。

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:178`
- `../ns-3.35/contrib/nr/model/nr-spectrum-phy.cc:140`
- `../ns-3.35/contrib/nr/model/nr-ue-phy.cc:577`

### 2.12 IPv6

- Release notes 明确写了端到端支持 IPv4 / IPv6。

依据：

- `../ns-3.35/contrib/nr/RELEASE_NOTES.md:118`

## 3. 部分支持，但不要误判成“完整支持”的能力

### 3.1 5QI：部分支持，不是原生 5GC QoS Flow

这份本地模块**没有原生的 SDAP / QoS Flow / 5GC 语义**，但它通过 `EpsBearer::Qci` 提供了 **Release 15 更新后的 QCI/5QI 数值集合**，并且 `NrHelper` 启动时会把 `ns3::EpsBearer::Release` 默认设为 `15`。

本地可见的值包括：

- `1, 2, 3, 4, 5, 6, 7, 8, 9`
- `65, 66, 67, 69, 70, 75, 79, 80, 82, 83, 84, 85`

因此更准确的结论是：

- **支持“用 Release 15 的 bearer/QCI 表来区分业务类别”**
- **不支持“5G SA 语义下的 QoS Flow + SDAP + 5QI 完整实现”**

依据：

- `../ns-3.35/contrib/nr/helper/nr-helper.cc:98`
- `../ns-3.35/src/lte/model/eps-bearer.h:106`

### 3.2 网络切片：只支持静态、RAN 侧近似

本地模块可以做的，是：

- 按 `QCI/业务类型 -> BWP` 进行静态映射
- 把不同流放进不同 BWP
- 用这种方式近似实现 **dedicated-resource RAN slicing**

但它不支持：

- `S-NSSAI / NSSAI`
- 5GC slice selection
- SDAP based QoS flow to DRB mapping
- 切片生命周期管理
- 动态切片编排

并且，默认 BWP manager 只有 **静态算法**，必须在仿真开始前配置。

因此这部分最准确的表述应当是：

- **支持“基于 BWP 的静态 RAN slicing 近似”**
- **不支持“完整 5G 网络切片”**

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:77`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:1290`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:1294`
- `../ns-3.35/contrib/nr/model/bwp-manager-algorithm.h:32`
- `../ns-3.35/contrib/nr/model/bwp-manager-algorithm.h:98`

### 3.3 “支持天线阵列”不等于“支持 MIMO”

这份代码支持：

- `UniformPlanarArray`
- 3GPP antenna element
- beamforming

但它**不支持空间复用层数带来的 SU-MIMO / MU-MIMO 吞吐提升**。

所以在你当前的 `nr-dce.cc` 里：

- `SetGnbAntennaAttribute ("NumRows", ...)`
- `SetGnbAntennaAttribute ("NumColumns", ...)`
- `SetUeAntennaAttribute (...)`

这些配置主要影响：

- 阵列增益
- 波束宽度
- 方向性
- 覆盖与 SINR

而**不会自动变成 2 层、4 层的数据空间复用**。

## 4. 明确不支持 / 文档明确列为缺失的能力

### 4.1 SU-MIMO / MU-MIMO / spatial multiplexing

这是最明确的结论。

文档在 `Scope and Limitations` 里直接写了：

- 缺少 `spatial multiplexing`

源码里还有多处佐证：

- gNB PHY 发数据时注释写着：`currently supports 1 user only`
- `DoSetTransmissionMode()` 基本没有真正实现
- gNB MAC 多处把 `m_transmissionMode = 0`，注释写明是 `SISO`
- UE MAC 多处把 `layer = 0`

所以：

- **SU-MIMO 不支持**
- **MU-MIMO 不支持**

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:1555`
- `../ns-3.35/contrib/nr/model/nr-gnb-phy.cc:1421`
- `../ns-3.35/contrib/nr/model/nr-gnb-phy.cc:1630`
- `../ns-3.35/contrib/nr/model/nr-gnb-mac.cc:629`
- `../ns-3.35/contrib/nr/model/nr-ue-mac.cc:659`

### 4.2 Configured grant scheduling

文档明确列为缺失。

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:1555`

### 4.3 Puncturing

文档明确列为缺失。

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:1555`

### 4.4 Control channel error model

文档明确列为缺失，源码里也有 “control error model not supported” 注释。

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:1557`
- `../ns-3.35/contrib/nr/model/nr-spectrum-phy.cc:1300`

### 4.5 SDAP

文档明确写明：

- `SDAP layer is not present yet in the 'NR' module.`

这也是为什么前面说 5QI 只能算“部分支持”。

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:1397`

### 4.6 5G SA / 5GC

这份本地模块不是 SA 架构，仍然依赖 LTE 的：

- RLC
- PDCP
- RRC
- NAS
- EPC
- X2

因此：

- **不支持真实 5GC/NG-RAN/SDAP/PDU Session 那一套 SA 语义**

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:28`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:1387`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:1393`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:1404`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:1410`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:1416`

### 4.7 运行时 BWP 重配置 / 默认 BWP RRC 配置

文档明确写明：

- 不支持 `default BWP` 的 RRC 配置消息
- 不支持 BWP reconfiguration
- 因此也不支持运行时 semi-static BWP 重配置

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:195`

### 4.8 重叠 BWP

本地实现要求 BWP 正交；重叠会导致干扰计算错误，因此不支持。

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:73`
- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:2004`

## 5. 需要谨慎对待的点

### 5.1 Handover 不建议默认当成“已可用能力”

我这次没有系统验证 handover 场景，但本地 `NrHelper` 源码里有很直接的注释：

- `SetDlEarfcn (0); // Argh... handover not working`
- `SetUlEarfcn (0); // Argh... handover not working`

所以如果你后面想做切换实验，建议单独再核查，不要把它直接当成“稳定支持”。

依据：

- `../ns-3.35/contrib/nr/helper/nr-helper.cc:816`

### 5.2 UE 同时活跃 BWP 能力有限

文档明确写了：

- gNB 可同时在多个 BWP 收发
- **UE 假设一次只活跃在一个 BWP**

所以即便你有多 BWP，也不要把它理解成 UE 侧完整多活动 BWP 模型。

依据：

- `../ns-3.35/contrib/nr/doc/source/nr-module.rst:200`

## 6. 对你当前 `myscripts/nr-dce/nr-dce.cc` 的直接影响

结合你当前脚本，我建议这样理解：

### 6.1 你现在配的“2x2 / 1x2 天线”不是 MIMO 吞吐层数

你当前写法：

- gNB：`NumRows=2`, `NumColumns=2`
- UE：`NumRows=1`, `NumColumns=2`
- `DirectPathBeamforming`

它们会影响链路预算和波束方向性，但**不会让本地 `nr` 自动变成 2-layer SU-MIMO 或 MU-MIMO**。

### 6.2 你现在能做的“业务隔离”，更适合走 BWP + QCI

如果你后续想做：

- eMBB / URLLC 业务分离
- 不同业务走不同 numerology
- 近似切片

本地最合适的做法不是找“真实网络切片 API”，而是：

1. 建多个 BWP
2. 用不同 numerology / 带宽 / TDD/FDD 配置
3. 用 `SetGnbBwpManagerAlgorithmAttribute()` / `SetUeBwpManagerAlgorithmAttribute()` 按 `EpsBearer::Qci` 做静态映射

### 6.3 如果你要写“理论速率”分析，别把 MIMO 乘数直接算进去

对这份本地模块，速率上限更应主要看：

- 带宽
- numerology
- TDD 配比
- MCS / AMC / error model
- scheduler
- SINR / beamforming

而不是把“手机 2T4R / gNB 4T4R”直接当作空间复用倍数乘进去。

## 7. 最后给一个简短判断

如果只用一句话概括这份本地 `nr` 模块：

> 它擅长的是 **Release-15 风格的 NR PHY/MAC 系统级仿真**，尤其是 `numerology + BWP + TDD/FDD + beamforming + scheduling + HARQ + QoS 类业务映射`；但它**不擅长也不原生支持** `SU/MU-MIMO 空间复用`、`完整 5QI/SDAP/5GC 语义`、`完整网络切片` 和 `5G SA`。
