# dce-wifi：160MHz / 2x2 吞吐仅 ~800Mbps 的原因排查记录（含参数科普）

日期：2026-03-16  
脚本：`myscripts/dce-wifi/dce-wifi.cc`（ns-3.35 + ns-3-dce + DCE Linux 4.4.110，iperf2）

这份记录的目标是两件事：

1) 复现实验并给出证据链（吞吐、TxVector 等）  
2) 让读者看懂“为什么改这些参数就会变快”（补齐必要概念）

## 0. TL;DR（给赶时间的读者）

缩写说明（首次出现先解释）：  
`MCS` = Modulation and Coding Scheme，调制与编码方案索引（如 `HE MCS11` 约等于 1024‑QAM 5/6）；  
`NSS` = Number of Spatial Streams，空间流数（`2SS` 表示 `NSS=2`，即 2 条空间流）；  
`GI` = Guard Interval，OFDM 保护间隔（常见 `800/1600/3200ns`，越短 PHY 速率越高）。

- **160MHz / 2SS / MCS11 实际已生效**：开启 `--printTxVector=1` 可看到 `HeMcs11 width=160MHz nss=2`。
- 在 **ns-3.35 原始默认** HE/MAC 参数下，TCP 吞吐只有 ~`0.78Gbps`：主要不是因为 MIMO/带宽没开，而是因为 **GI 偏长 + 聚合参数偏保守** 导致固定开销占比过高。
- 把 **HE GI / A‑MPDU 上限 / MPDU buffer** 调到更贴近高性能路由器（也更贴近“信号很好、单用户测速”的真实设备行为）后，TCP 吞吐可以到 `1.3~1.8Gbps`（本记录实测 `1.77Gbps`）。
- 备注：为方便“默认就更真实”，本脚本已将这些调优参数设为默认；如需复现 ns-3.35 原始默认行为，请按 §3.0/实验 A 的命令显式指定。

## 1. 背景知识：为什么 PHY 2.4Gbps ≠ iperf 2.4Gbps？

很多人第一次做 Wi‑Fi 仿真会直觉认为：

> 160MHz + 2x2 + MCS11 ≈ 2402Mbps（PHY）  
> 那 TCP 也应该接近 2.4Gbps

但真实/仿真都不会这么理想，原因在于 **“PHY 速率”只是空气接口的原始载荷速率**，上层还要扣掉大量固定开销。

### 1.1 三个常被混淆的“速率层次”

- **PHY data rate（TxVector/PHY 速率）**  
  由 `MCS + 带宽 + NSS + GI` 决定，反映“OFDM 符号里能塞多少数据比特 / 符号时长是多少”。
- **MAC throughput（MAC 层有效吞吐）**  
  还要扣：前导/信令、IFS（SIFS/DIFS）、竞争退避、ACK/BlockAck、重传等。
- **TCP goodput（应用层吞吐）**  
  还要扣：IP/TCP 头、拥塞控制/窗口限制、RTT/抖动、socket buffer 等。

本问题里：“PHY 速率”已经很高（2.0~2.4Gbps），但 TCP 却卡在 0.8Gbps，典型就是 **MAC 固定开销占比过高（聚合不够）**。

### 1.2 802.11 的固定开销为什么会把高 MCS 打残

在高速率（例如 160MHz、1024‑QAM、2SS）下，**每个 PPDU 的固定开销占比会变得非常大**，主要包括：

- Preamble / SIG（前导与信令字段）
- IFS（SIFS/DIFS）
- 竞争退避（Backoff）
- ACK / BlockAck（尤其是非聚合或聚合很小的时候）

所以，高速 Wi‑Fi 想逼近 PHY，关键不是再抬 MCS，而是 **把“每次占用信道的有效载荷”做大（聚合）**，用大帧把固定开销摊薄。

## 2. 本实验的场景与证据来源

### 2.1 拓扑与业务

- 1 个 AP（4x4）
- 1 个 STA（2x2）
- 距离 1m（信道条件非常好）
- STA 作为 iperf client，AP 作为 iperf server（TCP）

### 2.2 信道/速率控制的默认假设

- 信道：`YansWifiChannelHelper::Default()`，默认是“光速传播时延 + LogDistance 路损（1m 参考损耗 46.6777dB）”。  
  这不是 TGax 的复杂室内信道模型；在 1m、无干扰的条件下 SNR 会非常高。
- 速率控制：`IdealWifiManager`（理想化：基于 SNR 阈值挑理论最优 MCS/NSS），因此在这个场景里很容易跑到最高 MCS/NSS。

### 2.3 证据来自哪里

- **TxVector 证据**：脚本提供 `--printTxVector=1`，在 STA 的 `PhyTxPsduBegin` trace 上打印 TxVector 变化：
  - `MCS`（例如 `HeMcs11`）
  - `width`（MHz）
  - `nss`（空间流数）
  - `gi`（ns）
  - 对应的 PHY `dataRate`（Mbps）
- **吞吐证据**：DCE 里的 iperf 输出写在当前目录生成的 `files-0/`（STA）和 `files-1/`（AP）下：
  - `files-0/var/log/<pid>/stdout`：client 输出
  - `files-1/var/log/<pid>/stdout`：server 输出

## 3. 关键参数详解（概念 + 本脚本如何映射到 ns-3）

`myscripts/dce-wifi/dce-wifi.cc` 暴露了一些可调参数，目的是让你能“单变量”验证瓶颈在哪。

### 3.0 参数速查表（ns-3.35 原始默认 vs 本脚本默认）

> 右列的“本脚本默认”是针对本实验（1m、理想信道、追求接近真实设备的高吞吐）做的调整；更复杂/更差信道时，需要在“吞吐 vs 稳健性/误码率”之间折中。  
> 如果你想复现 ns-3.35 原始默认行为，请在命令行显式指定左列（见实验 A）。

| 参数 | ns-3.35 原始默认 | 本脚本默认（更贴近真实测速） | 主要影响 | 备注 |
|---|---:|---:|---|---|
| `--heGuardIntervalNs` | 3200 | 800 | PHY 速率 | GI 越短速率越高；信道差时更可能错包 |
| `--heMpduBufferSize` | 64 | 256 | A‑MPDU 可聚合 MPDU 数 | 过小会限制聚合/重排序能力 |
| `--beMaxAmpduSize` | 65535 | 6500631 | A‑MPDU 字节上限 | 设到 HE cap 相当于“取消该限制”（仍受 PPDU 时长等限制） |
| `--tcpSockBufMaxBytes` | 0 | 16777216 | TCP window 上限 | 让 iperf `-w 8M` 更接近真实系统表现 |
| `--printTxVector` | 0 | 0 | 输出 MCS/宽度/NSS/GI | 排查/对照时手动设为 1 |

### 3.1 `--channelWidthMhz` / `--frequencyMhz`：带宽与中心频点

- `--channelWidthMhz`（默认 160）：设置 `WifiPhy::ChannelWidth`。
  - 20/40/80/160MHz 是典型配置；带宽翻倍一般能把 PHY 速率近似翻倍。
- `--frequencyMhz`（默认 5250）：设置 `WifiPhy::Frequency`。
  - `5250MHz` 是 5GHz 下覆盖 CH36~CH64 的 160MHz 组合信道的中心频率（常见“从 36 起 160MHz”）。

注意：带宽和频点只是“资源规模”，并不能保证吞吐高；吞吐还高度依赖聚合把固定开销摊薄。

### 3.2 2x2 / 4x4 与 `nss`：空间流数（NSS）到底是什么？

常见表述：

- “2x2 MIMO”通常意味着终端可支持 **最多 2 条空间流（NSS=2）**（不考虑更复杂的 MU‑MIMO/OFDMA）。
- AP 4x4、STA 2x2 时，单用户上下行能用的空间流通常受 STA 限制（NSS=2）。

本脚本分别在安装设备前设置：

- AP：`Antennas=4`、`MaxSupportedTxSpatialStreams=4`、`MaxSupportedRxSpatialStreams=4`
- STA：`Antennas=2`、`MaxSupportedTxSpatialStreams=2`、`MaxSupportedRxSpatialStreams=2`

如何验证“确实用到了 2SS”？看 `--printTxVector` 输出里的 `nss=2`。

### 3.3 MCS：`HeMcs11` 代表什么？

以 802.11ax（HE）为例：

- `HeMcs11` 对应 **1024‑QAM 5/6**（最高调制阶数与较高码率），单位符号携带比特数最高。
- MCS 越高，对信道条件要求越高；本实验 1m、无干扰，理想条件下很容易锁到最高 MCS。

本脚本用 `IdealWifiManager`，会更倾向于“在好信道下把 MCS/NSS 拉满”，从而更容易暴露“聚合/开销”问题。

### 3.4 `--heGuardIntervalNs`：HE Guard Interval（GI，800/1600/3200ns）

**GI 是 OFDM 符号间的保护间隔**，用来抵抗多径导致的符号间干扰。

- GI 越短：符号越“紧凑”，单位时间内符号数更多 → PHY 速率更高
- GI 越长：更稳健但速率下降

ns-3.35 的 HE GI 默认是 `3200ns`（更稳健但更慢）。在本实验这种理想信道下，这个默认值会显得偏保守。

#### 3.4.1 用公式算一遍：为什么 GI=800ns 时 PHY 约 2402Mbps？

对 **HE SU、160MHz、2SS、MCS11（1024‑QAM 5/6）**：

- 数据子载波数 `Nsd(160MHz)=1960`
- 每子载波比特 `Nbpscs=10`
- 编码率 `R=5/6`
- 空间流 `NSS=2`
- 符号时长 `Tsym = 12.8us + GI`

理论 PHY 速率近似为：

```
Rate ≈ Nsd * Nbpscs * R * NSS / Tsym
```

- GI=800ns：`Tsym=13.6us` → `Rate≈2401.96Mbps`
- GI=3200ns：`Tsym=16.0us` → `Rate≈2041.67Mbps`

这与脚本打印的 TxVector `dataRate≈2401.96 / 2041.67` 一致。

### 3.5 A‑MPDU（聚合）与两个关键限制参数

#### 3.5.1 先区分 MPDU / A‑MPDU

- **MPDU**：802.11 MAC 帧（带 MAC Header/CRC）
- **A‑MPDU**：把多个 MPDU 拼在一次 PHY 发送机会里（配合 BlockAck），是提升吞吐的关键

在高速率下，如果每次只发很小的 MPDU，Preamble/IFS/ACK 的相对占比会很大，所以吞吐会掉到几百 Mbps。

#### 3.5.2 `--beMaxAmpduSize`：限制 A‑MPDU 的“字节数上限”

本脚本把它映射到 `RegularWifiMac` 的属性 `BE_MaxAmpduSize`（单位：bytes）。

- ns-3.35 默认（AC_BE）：`65535` bytes  
  对 HE 来说偏小（更像 HT 时代的默认量级）。
- 在 ns-3 的实现里，HE PPDU 的 A‑MPDU 上限会被 cap 到 `6500631` bytes。

**把 `BE_MaxAmpduSize` 提高**，就允许 MAC 聚合器把更多 MPDU 聚到一个 A‑MPDU 里，从而显著降低 ACK/IFS/竞争开销占比。  
注意：增大上限并不意味着每次都会聚到这么大，ns-3 里还有 PPDU 时长等其它约束；但如果上限太小，会直接“卡死”聚合规模。

#### 3.5.3 `--heMpduBufferSize`：限制“接收端能接住多大的 A‑MPDU”

本脚本把它映射到 `HeConfiguration::MpduBufferSize`（范围 64~256）。

直观理解：接收端用于重排序/接收 A‑MPDU 的 MPDU 缓冲能力。  
如果这个值小，发送端即使想聚合更大，也会因为对端能力限制而聚不上去（或触发其它限制）。

#### 3.5.4 这两个限制如何一起“卡死”吞吐（直观算例）

下面用一个“量级估算”帮助理解默认值为什么容易把吞吐压到 1Gbps 以下：

- 典型 TCP MSS≈1460B，算上 MAC/QoS/分隔等开销，一个 MPDU 的量级可粗略认为在 ~`1500B` 左右。
- `MpduBufferSize=64` 代表接收端在一个 A‑MPDU 里最多能处理 ~64 个 MPDU，payload 量级约 `64*1500B≈96KB`。
- 但基线下 `BE_MaxAmpduSize=65535B` 又把 A‑MPDU 的**字节数**进一步卡到 ~`64KB`，相当于最多也就几十个 MPDU（约 40 个量级）。
- 在 `~2.0Gbps` 的 PHY 下，`64KB` 纯 payload 的空口发送时间大约 `512kbit / 2Gbit/s ≈ 0.25ms`；但每次发送还要付出 Preamble/IFS/Backoff/BlockAck 等固定开销（数量级上百微秒甚至更多）。聚合越小，这些固定开销占比越高，吞吐就越低。
- 当把 `MpduBufferSize` 提到 256、并把 `BE_MaxAmpduSize` 提到 HE cap 时，聚合器不再被这两个“人为上限”限制，更容易把固定开销摊薄，从而显著提升吞吐。

### 3.6 `--tcpSockBufMaxBytes`：DCE Linux 的 socket buffer / TCP window 上限

你会在 iperf 输出里看到类似：

- `TCP window size: 416 KByte (WARNING: requested 8.00 MByte)`

这表示 iperf `-w 8M` 是“请求”，但内核没给到那么大（受 sysctl 上限影响）。

本脚本的 `--tcpSockBufMaxBytes` 会在 DCE Linux 里设置（例如 16MiB）：

- `.net.core.rmem_max` / `.net.core.wmem_max`
- `.net.ipv4.tcp_rmem` / `.net.ipv4.tcp_wmem`（把第三个值设为 max）

为什么窗口会影响吞吐？粗略上限是：

```
Throughput <= Window / RTT
```

在“Wi‑Fi 聚合已经做得很好”的前提下，窗口/RTT 才更容易变成下一个瓶颈，所以这通常是“第二阶段调参”。

> 一个帮助直觉的估算：如果 RTT≈2ms，那么 `416KB` 的窗口理论上限约为 `416KB / 2ms ≈ 1.7Gbps`。  
> 这解释了为什么在本实验里“只调大 TCP buffer（实验 B）”对基线吞吐几乎没帮助：因为真正的第一瓶颈还在 Wi‑Fi 的聚合/开销上。

### 3.7 `--printTxVector`：用于证明“到底跑在什么 PHY 上”

开启后会打印类似：

- `HeMcs11 width=160MHz nss=2 gi=3200ns dataRate=2041.666668Mbps`
- `HeMcs11 width=160MHz nss=2 gi=800ns dataRate=2401.960786Mbps`

这能快速排除两类常见误判：

1) 其实没跑到 160MHz 或没跑到 2SS  
2) 其实没跑到高 MCS（速率选择器没选上去）

### 4.1 运行准备

1) 编译：

```bash
./waf build
```

2) 设置 DCE_PATH（否则会报 `Executable 'iperf' not found`）：

### 4.2 关键确认：160MHz 与 2SS 实际生效（TxVector 证据）

```bash
# ns-3.35 原始默认（HE GI=3200ns）
./build/myscripts/dce-wifi/bin/dce-wifi --iperfTimeSec=3 --printTxVector=1 --heGuardIntervalNs=3200

# 短 GI（HE GI=800ns；本脚本默认就是 800ns，也可以不带该参数）
```

- 默认 HE GI（3200ns）：`HeMcs11 width=160MHz nss=2 gi=3200ns dataRate≈2041.67Mbps`

结论：`160MHz`、`2SS`、`MCS11` 都已生效；吞吐 ~800Mbps 不是因为“没跑到 160/2SS”。

```bash

  --heGuardIntervalNs=3200 \
  --heMpduBufferSize=64 \
  --beMaxAmpduSize=65535 \
```

- `TCP window size: 416 KByte (WARNING: requested 8.00 MByte)`
- `0.0- 5.0 sec  465 MBytes  780 Mbits/sec`

### 4.4 实验 B：只调大 TCP buffer（不改 Wi‑Fi 聚合）

```bash
./build/myscripts/dce-wifi/bin/dce-wifi \
  --iperfTimeSec=10 \
  --heGuardIntervalNs=3200 \
  --heMpduBufferSize=64 \
  --beMaxAmpduSize=65535 \
  --tcpSockBufMaxBytes=16777216
```

client 摘要：

- `TCP window size: 16.0 MByte ...`
- `0.0-10.0 sec  936 MBytes  785 Mbits/sec`

结论：单纯放大 TCP window，吞吐几乎不变；说明 ~800Mbps 的主因并不是 TCP buffer。

```bash
./build/myscripts/dce-wifi/bin/dce-wifi \
```

- `0.0- 5.0 sec  1.03 GBytes  1.77 Gbits/sec`


| 组别 | Wi‑Fi（GI/聚合） | TCP buffer | 吞吐（TCP） |

## 5. 根因总结：为什么“160MHz/2x2”却只有 ~800Mbps？

本实验里，`160MHz/2SS/MCS11` 都是 OK 的（见 TxVector 证据），但基线吞吐低，主要因为：

1) **默认 HE GI=3200ns**：PHY 速率从 ~2402Mbps 降到 ~2042Mbps（上限直接少一截）  
2) **更关键：默认聚合参数限制了 A‑MPDU 的规模**  
   - `HeConfiguration::MpduBufferSize` 默认 64  
   - `RegularWifiMac::BE_MaxAmpduSize` 默认 65535（对 HE 来说偏小）  
   导致每次占用信道的有效载荷不够大，固定开销占比高 → TCP 吞吐被“开销”锁在 ~800Mbps

从“效率”（TCP goodput / PHY data rate）的角度看更直观：

- 基线（GI=3200ns）：PHY≈`2.04Gbps`，TCP≈`0.78Gbps`，效率≈`38%`
- 调优（GI=800ns）：PHY≈`2.40Gbps`，TCP≈`1.77Gbps`，效率≈`74%`

TCP buffer 在基线下不是主因；但当聚合充分后，TCP buffer 会成为“下一个瓶颈”，所以调大后能进一步从 ~1.3Gbps 推到 ~1.7Gbps。

## 8. Wi‑Fi 概念课：MCS / (HE)GI / A‑MPDU / HE‑MAC（学习章节）

这一章不依赖 ns-3，主要讲 802.11（尤其 802.11ax / HE）里和“吞吐为什么上不去”最相关的几个概念，并给出足够的直觉，让你以后看任何 Wi‑Fi 吞吐问题都有抓手。

### 8.1 先把“层次”理清：PHY vs MAC vs TCP

可以把 Wi‑Fi 吞吐理解成从下往上逐层扣“成本”：

```
PHY data rate  --(Preamble/SIG, IFS, Backoff, ACK/BA, 重传...)-->  MAC throughput
MAC throughput --(IP/TCP头, 拥塞控制/窗口, RTT/排队...)-->          TCP goodput (iperf看到的)
```

所以“看到 PHY 很高，但 iperf 很低”时，通常意味着：

- 要么 **MAC 固定开销占比太大**（最常见：聚合不够）
- 要么 **TCP 窗口/拥塞控制** 限制了上层（常见于高 RTT、buffer 太小或多跳/丢包）

本实验属于第一类为主：聚合做大后，才轮到 TCP buffer 成为第二阶段瓶颈。

### 8.2 MCS 是什么？它决定了“每个子载波每个符号能塞多少比特”

**MCS（Modulation and Coding Scheme）** 是“调制方式 + 编码率”的组合索引：

- 调制（星座图）决定：每个子载波每个符号携带多少比特  
  例如 BPSK=1、QPSK=2、16‑QAM=4、64‑QAM=6、256‑QAM=8、1024‑QAM=10（bit/subcarrier/symbol）
- 编码率（如 1/2、2/3、3/4、5/6）决定：这些比特里有多少是有效信息，有多少是纠错冗余

对于 802.11ax（HE），常见 `MCS0~MCS11`，其中 `HE MCS11` ≈ 1024‑QAM 5/6（很“激进”，对信道条件要求高）。

但 **MCS 只是一部分**。真正的 PHY 速率还取决于：

- 带宽（20/40/80/160MHz）：子载波数量随带宽增加
- **NSS（Number of Spatial Streams）**：空间流数（2x2 终端通常 NSS≤2）
- **GI（Guard Interval）**：符号保护间隔（会改变符号时长）

### 8.3 NSS / 2SS：空间流数为什么会让速率“乘以 2”

**NSS** 是“并行空间流”的数量。直觉上：

- `NSS=1`：一次发 1 份数据流
- `NSS=2`：在同一时间/频率资源上并行发 2 份独立数据流（需要多天线与合适的信道条件）

所以在相同 MCS、带宽、GI 下，PHY 速率大致与 NSS 成正比（2SS 接近 2 倍）。

在本脚本里，我们用 `--printTxVector` 直接看到 `nss=2`，证明“2x2 真的在跑 2SS”。

### 8.4 GI / HE GI：为什么 GI 一改，PHY 速率就变了

**GI（Guard Interval）** 是 OFDM 符号之间的保护间隔，用来抵抗多径导致的符号间干扰。

- GI 越短：每个符号总时长越短 → 单位时间符号数更多 → PHY 速率更高
- GI 越长：更稳健，但 PHY 速率下降

802.11ax（HE）里常见的 HE GI 选项是：

- `800ns`、`1600ns`、`3200ns`

并且 HE 的 OFDM 符号有效部分是 `12.8us`，所以总符号时长：

```
Tsym = 12.8us + GI
```

这就是为什么同样 `HeMcs11/160MHz/2SS`：

- GI=800ns 时可以到 ~2402Mbps
- GI=3200ns 时只有 ~2042Mbps

> 现实世界里，GI 不是“越短越好”。在多径严重、延迟扩展大的环境里，过短的 GI 会带来更高误码率/重传，最终吞吐反而下降。本实验 1m 理想信道属于“短 GI 更合适”的一类。
>
> 另外需要注意：**ns-3.35 的 Wi‑Fi 模块里，HE GI 通常是固定配置值**（来自 `HeConfiguration::GuardInterval`），默认不会像真实设备那样在 800/1600/3200ns 之间按链路状态“自适应”。如果你想研究 GI 自适应，需要自己实现策略（例如扩展 `WifiRemoteStationManager`/`WifiRemoteStationManager` 的 TXVECTOR 生成逻辑，或在仿真过程中动态修改配置）。

### 8.5 A‑MPDU 是什么？为什么它几乎决定你能不能接近 PHY

先把三个单位区分开：

- **MSDU**：上层交给 802.11 的业务数据（可以类比“以太网 payload”）
- **MPDU**：802.11 MAC 帧（带 MAC Header/CRC）。一个 MPDU 通常承载一个 MSDU（或 A‑MSDU）
- **A‑MPDU**：把多个 MPDU 拼在一次传输机会里发送，并用 **BlockAck（BA）** 一次性确认多帧

在高速率下（160MHz + 高 MCS + 多流），如果每次只发 1 个小 MPDU，你会为每次发送付出：

- Preamble/SIG
- IFS + Backoff（竞争信道的成本）
- ACK/BA（确认的成本）

这些成本很多是“固定的”，与 payload 大小无关。  
**A‑MPDU 的核心价值**：一次占用信道，塞进去更多 MPDU，把固定开销摊薄，吞吐就上来了。

### 8.6 HE‑MAC / HE‑PHY 都包含什么？本实验到底用到了哪些

**HE（High Efficiency）= 802.11ax**，它同时改了 PHY 和 MAC：

- HE‑PHY 侧常见能力：1024‑QAM、OFDMA（RU）、不同 HE GI/HE‑LTF、更多带宽组合等
- HE‑MAC 侧常见能力：OFDMA 调度（触发帧）、BSS Color、MU‑EDCA、TWT、省电/调度机制等

但不是每个 ax 场景都会用到所有特性。本实验更像“高端路由器 + 单终端的极限跑分”：

- 主要用到：**HE SU（单用户）+ 高 MCS + 2SS + 160MHz + A‑MPDU 聚合**
- 基本没用到：OFDMA RU 调度、复杂 MU 机制、密集 BSS 干扰下的 BSS color 等

所以你看到“把聚合相关参数调大后吞吐暴涨”，非常符合 SU 极限吞吐问题的典型规律。

### 8.7 把概念落到本脚本：哪些参数分别在控制什么

本实验里最关键的三类控制旋钮：

1) **PHY 速率旋钮**：`MCS / NSS / 带宽 / GI`  
   - `MCS/NSS/宽度/GI` 最终体现在 TxVector（`--printTxVector`）
   - `--heGuardIntervalNs` 直接改变 HE GI，从而改变 PHY data rate
2) **MAC 效率旋钮**：A‑MPDU 聚合规模  
   - `--beMaxAmpduSize`：限制 A‑MPDU 的最大字节数（太小会“卡死”聚合）
   - `--heMpduBufferSize`：限制接收端可处理的 A‑MPDU MPDU 数（太小也会限制聚合）
3) **TCP 层旋钮**：窗口/缓冲  
   - `--tcpSockBufMaxBytes`：提高 DCE Linux 下 rmem/wmem/tcp_rmem/tcp_wmem 上限，允许更大的 TCP window

经验上排查顺序通常是：

1) 先用 TxVector 证明 PHY 配置确实生效（宽度/NSS/MCS/GI）
2) 再看聚合（A‑MPDU）是不是被默认值卡住
3) 最后才是 TCP buffer/窗口/拥塞控制
