## 对这个现象的解释

从“参数已经生效、结果却没变”这一点看，可以得出一个比较稳的结论：

- 当前多设备性能问题的主因，不是这个默认值从 `6` 到 `0` 的变化。

更具体地说，有两种较合理的解释：

1. `wifiMuSchedulerStations` 在这个场景里不是主导瓶颈。  
   即使把一次调度允许的站点数放大，真正限制性能的仍然可能是其他 Wi-Fi MAC/PHY 机制、排队、Block Ack、触发帧流程或空口竞争。

2. 这个参数的主要影响方向更偏向 DL MU PPDU，而当前场景是 STA 向 server 的 uplink UDP。  
   脚本里该参数的说明本身就是：
   “Maximum stations granted an RU in one DL MU PPDU”

这里第 2 点是根据参数命名和注释做出的**合理推测**，不是这轮实验直接证明的事实。  
这轮实验直接证明的事实是：

- 默认值已改成 `0`
- 运行时也确实变成了 `muStations=9/30`
- 但吞吐、时延、公平性指标没有出现可见改善

## 本轮小结

本轮实验可以明确回答：

- 把默认 `wifiMuSchedulerStations` 从 `6` 改成 `0` 是可以的，代码已经改好。
- 但对当前这组 `9` 台、`30` 台 uplink 测试结果，几乎没有带来可见变化。

因此，如果下一步还想继续改善 `30` 台的表现，更值得优先排查的方向不是“默认值 6 改成 0”，而是：

1. 多 AP 分流
2. 更低 offered load 工作点
3. 其他 MU/OFDMA/Block Ack 相关参数
4. 当前 uplink 调度路径的真正瓶颈
