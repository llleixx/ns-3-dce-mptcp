# 多设备实测记录（2026-04-06）

## 先看结论

这次参考 `myscripts/120-demo/link-info/wifi-only/多设备实测记录-20260406.md` 的写法，补了 `myscripts/120-demo/link-info/nr-only/link-info-nr-only.cc` 在 `9` 台和 `30` 台 client 下的多设备结果。

- 对 `9` 台来说，总净 payload 吞吐平台大约在 `387-388 Mbps`。
- `9` 台在 `40 Mbps/台` 时仍然比较健康，总吞吐约 `352 Mbps`，平均单向时延约 `3.27 ms`。
- `9` 台一旦提高到 `45 Mbps/台`，总吞吐已经几乎封顶，但平均单向时延会立刻跳到 `74 ms`；`50 Mbps/台` 及以上则迅速进入数百毫秒到秒级。
- 对 `30` 台来说，`10 Mbps/台` 仍然是可用工作点，总吞吐约 `288 Mbps`，平均单向时延约 `3.75 ms`。
- `30` 台提高到 `15 Mbps/台` 后，总吞吐升到约 `366 Mbps`，已经接近小区总上限，但平均单向时延也暴涨到 `423 ms`。

如果只看当前默认 NR 参数下“高吞吐 + 低时延”的区间，那么比较保守的建议是：

- `9` 台：约 `40 Mbps/台`
- `30` 台：约 `10 Mbps/台`

## 改动情况

本次没有修改 `link-info-nr-only.cc`、ns-3 或 ns-3-dce 源码，只做参数扫描和结果记录。

## 测试目的

单设备测试只回答“一个 UE 独占上行时能跑多快”。  
但多设备场景更关心：

- 多个 UE 同时上行时，总吞吐还能达到多少。
- 每个 UE 大概还能分到多少吞吐。
- 在什么每用户 offered load 下，时延会开始明显恶化。
- `9` 台和 `30` 台这两种数量级下，多用户共享一个 gNB 时表现差异有多大。

## 指标口径

与 Wi-Fi 脚本不同，当前 NR 脚本只输出一套吞吐：

- `aggregateThroughputMbps`：按 sink 端收到的 `packet->GetSize()` 统计，**不包含** `SeqTsSizeHeader`，因此它是 **净应用层 payload 吞吐**
- `meanDelayMs`：基于 `SeqTsSizeHeader` 时间戳计算的单向应用层平均时延
- `lossRatePct`：根据接收序号间断推断的应用层丢失比例
- `minFlowThroughputMbps / maxFlowThroughputMbps`：每流吞吐最小/最大值，用来看公平性

这里最容易误解的是：`offeredLoadMbpsPerClient` 的口径和 `aggregateThroughputMbps` 的口径并不完全一致。

- `offeredLoadMbpsPerClient` 作用在 `OnOffApplication` 的 `packetSize=1400 B`
- 其中 `20 B` 是 `SeqTsSizeHeader`
- 所以如果链路不丢包，净 payload 的理论上限是：

```text
offeredLoadMbpsPerClient * (1400 - 20) / 1400
```

例如：

- `40 Mbps/台` 的理论净吞吐约为 `39.429 Mbps/台`
- `10 Mbps/台` 的理论净吞吐约为 `9.857 Mbps/台`

因此下面分析“是否接近 offered load”时，需要按这个净 payload 口径理解。

### 关于 `lossRatePct=0`

高负载时，下面一些点会出现：

- 吞吐已经封顶
- 时延非常大
- 但 `lossRatePct` 仍然是 `0`

这并不代表场景没有问题。更合理的解释是：

- 报文主要是在 RLC/MAC/调度路径里排队等待
- 在 `8 s` 仿真结束前，很多报文还没有变成“序号缺口”被 sink 观察到
- 所以 `lossRatePct` 没有反映出“来不及送达”的那部分压力

因此在当前 NR 脚本里，高负载时应当更重视：

- 吞吐是否已进入平台期
- `meanDelayMs` 是否已经明显恶化

## 9 台结果分析

### 1. 总容量

`9` 台场景下，总净 payload 吞吐平台大约在：

- `387-388 Mbps`

这个结果与单设备时测得的净 payload 吞吐上限 `389 Mbps` 很接近。  
也就是说，在当前默认 NR 参数下，`9` 台并不会把小区总上行能力线性叠加到 `9` 倍，而是共享同一个总容量池。

### 2. 可用工作点

如果把“可用”理解为：

- 吞吐已经比较高
- 平均单向时延仍然只有几毫秒

那么当前测得的较优工作点大约是：

- `40 Mbps/台`

此时：

- 总净吞吐约 `352 Mbps`
- 平均单向时延约 `3.27 ms`
- 每流吞吐分布也很均匀

而一旦提高到 `45 Mbps/台`：

- 总吞吐只增加到 `386.6 Mbps`
- 但平均单向时延会跳到 `74.1 ms`

所以 `40 -> 45 Mbps/台` 就是很明显的时延拐点。

### 3. 公平性

`9` 台在低负载和中负载下公平性很好，例如：

- `20 Mbps/台` 时每流约 `19.44-19.71 Mbps`
- `40 Mbps/台` 时每流约 `38.88-39.40 Mbps`

进入平台期后，公平性开始变差，但幅度还不算特别夸张，例如：

- `45 Mbps/台` 时每流约 `40.45-43.92 Mbps`
- `100 Mbps/台` 时每流约 `40.44-44.42 Mbps`

这说明 `9` 台场景的主要问题是总队列积压，而不是极端不公平。

## 30 台结果分析

### 1. 总容量

`30` 台时，总净 payload 吞吐同样没有突破单小区总能力的量级。  
从已测点看：

- `10 Mbps/台` 时总净吞吐约 `288 Mbps`
- `15 Mbps/台` 时总净吞吐约 `366 Mbps`

结合单设备和 `9` 台结果，可以看出当前默认 NR 参数下的小区总净 payload 吞吐上限仍然大致落在：

- `370-390 Mbps`

也就是说，`30` 台只是把这份总能力在更多 UE 之间分摊，而不是把总能力继续堆高很多。

### 2. 可用工作点

当前测到的 `30` 台较稳妥工作点大约是：

- `10 Mbps/台`

此时：

- 总净吞吐约 `288 Mbps`
- 平均单向时延约 `3.75 ms`
- 每流吞吐约 `9.37-9.85 Mbps`

提高到 `15 Mbps/台` 后：

- 总吞吐虽然提高到 `366 Mbps`
- 但平均单向时延直接恶化到 `422.9 ms`

所以对 `30` 台来说，`10 -> 15 Mbps/台` 已经跨过了“高吞吐可用区”和“排队过载区”的边界。

### 3. 公平性

`30` 台在低到中负载时公平性仍然不错，例如：

- `8 Mbps/台` 时每流约 `7.50-7.88 Mbps`
- `10 Mbps/台` 时每流约 `9.37-9.85 Mbps`

到 `15 Mbps/台` 时差距开始明显扩大：

- 每流约 `10.73-13.93 Mbps`

这说明高负载下不同 UE 的服务机会已经开始拉开。

### 4. 墙钟时间

`30` 台场景还有一个很实际的现象：  
即使仿真结果本身还没坏掉，墙钟运行时间也会在更高负载点明显增长。

例如：

- `8 Mbps/台` 和 `10 Mbps/台` 都能完成，但比低负载点慢很多
- `15 Mbps/台` 更慢，而且结果也已经显示出明显排队恶化

所以后续如果要做更密集的 `30` 台扫描，建议：

- 只在 `8-15 Mbps/台` 这个区间挑少量关键点
- 不要像单设备那样每 `1 Mbps` 都扫一遍

## 与 Wi-Fi 多设备结果的对照

如果只和同一天的 Wi-Fi 多设备记录做现象级对照，可以看到几个明显差别：

- Wi-Fi `30` 台在很低每用户负载下就已经出现很高时延，而当前 NR `30` 台到 `10 Mbps/台` 仍然能维持几毫秒级时延。
- NR `9` 台和 `30` 台的总容量都更明显地“卡在同一个单小区总能力上”，只是用户越多，每个用户分到的份额越小。
- NR 高负载时也会进入严重排队区，但拐点比 Wi-Fi 更晚，且在当前已测点里还没有出现 Wi-Fi 那种很早就失控的情况。

需要注意：

- Wi-Fi 记录主表优先用 `grossThroughputMbps`
- 这里 NR 记录只有 `aggregateThroughputMbps`，它是 **net payload** 口径

因此两者可以做趋势对照，但不要把表中的数值当成完全同口径的“绝对带宽”直接横着比。

## 小结

在 `link-info-nr-only.cc` 当前默认 NR 参数下：

- `9` 台总净 payload 吞吐平台约 `387-388 Mbps`
- `9` 台较合理工作点约 `40 Mbps/台`
- `30` 台较合理工作点约 `10 Mbps/台`
- `30` 台提高到 `15 Mbps/台` 后，总吞吐虽接近 `366 Mbps`，但平均单向时延会恶化到 `423 ms`

因此，当前默认参数下 NR 多设备场景的主要特征可以概括为：

- 小区总上行能力大致固定在单小区总容量量级
- 用户数增加后，主要变化是“每用户可分配吞吐下降”
- 一旦每用户 offered load 继续上推，系统先表现为排队时延快速恶化，而不是总吞吐继续线性增长
