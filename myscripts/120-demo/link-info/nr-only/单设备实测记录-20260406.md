# 单设备实测记录（2026-04-06）

## 先看结论

本次只看 `1` 个 NR client、`1` 个 gNB 的情况，不改 `myscripts/120-demo/link-info/nr-only/link-info-nr-only.cc` 源码，只扫描 `offeredLoadMbpsPerClient`。

- 在当前默认 NR 参数下，单 client 的 **应用层净 payload 实收吞吐上限** 大约是 `389 Mbps`。
- 低负载到中负载时，平均单向应用层时延大致在 `3.0-3.2 ms`。
- 如果同时追求“高吞吐 + 低时延”，比较稳妥的工作点在 `394-395 Mbps` offered load 附近，此时实收吞吐约 `388-389 Mbps`，平均单向时延约 `3.4-4.4 ms`。
- 一旦继续把 offered load 推到 `396 Mbps` 及以上，吞吐几乎不再增加，但平均时延会从 `11.9 ms` 很快爬升到 `41.9 ms`，再往上甚至进入数百毫秒到秒级。

## 指标口径说明

- “带宽”这里记录的是脚本输出的 `aggregateThroughputMbps`。
- 这个值按 sink 端收到的 `packet->GetSize()` 统计，**不包含** `SeqTsSizeHeader`，因此它对应的是 **净应用层 payload 吞吐**。
- “延迟”这里记录的是 `meanDelayMs`，即 sink 端按 `Simulator::Now() - header.GetTs()` 计算的 **单向应用层时延**。
- 当前脚本的 `lossRatePct` 是根据收到的数据包序号间断推断的；如果仿真结束时还有报文堵在队列里、根本没来得及到达 sink，这部分不一定会体现在 `lossRatePct` 里。因此高负载时即使 `lossRatePct=0`，也不代表没有明显排队。

从 `300 Mbps` offered load 时实收约 `295.6 Mbps` 可以验证这一点：

- `300 * (1400 - 20) / 1400 = 295.714 Mbps`

这与实测值基本一致，说明当前吞吐口径确实是去掉 `20 B` `SeqTsSizeHeader` 后的净 payload 吞吐。

## 结果分析

### 1. 单 client 能达到多少带宽？

如果把“带宽”理解为当前脚本输出的应用层净 payload 实收吞吐，那么单 client 的上限大约是：

- `389 Mbps`

这个值不是 PHY 标称速率，而是 server 端应用层真正收到的净 payload 速率。

### 2. 单 client 的延迟能达到多少？

这个问题需要分负载区间回答：

- 低负载/中负载时：平均单向时延大约 `3.0-3.2 ms`
- 高吞吐但仍可用时：大约 `3.4-4.4 ms`
- 冲极限吞吐时：从 `11.9 ms` 快速恶化到 `41.9 ms`
- 明显过载时：可进一步进入 `370 ms` 到 `1 s+`

因此，这个场景下不能只报一个“NR 单 client 时延”数字；更合理的说法是：

- “空闲到中载时延”约 `3 ms`
- “高吞吐可用时延”约 `4 ms`
- “硬顶极限吞吐时延”则会迅速劣化到几十毫秒甚至更高

### 3. 推荐工作点

如果目标是“尽量高的吞吐，同时不把时延拖垮”，建议把单 client offered load 控制在：

- `394-395 Mbps`

这个区间里：

- 实收吞吐约 `388-389 Mbps`
- 平均单向时延约 `3.4-4.4 ms`
- 已经非常接近链路上限

如果只是追求“冲到极限吞吐”，那么把 offered load 提到 `396-400 Mbps` 也只能维持几乎相同的 `389 Mbps` 实收吞吐，但时延会显著恶化，通常不适合作为“可用带宽”来引用。

## 小结

在 `myscripts/120-demo/link-info/nr-only/link-info-nr-only.cc` 当前默认 NR 参数下，`1` 个 client 的表现可以概括为：

- 单 client 应用层净 payload 实收吞吐上限约 `389 Mbps`
- 低负载到中负载平均单向时延约 `3.0-3.2 ms`
- 较合理的高吞吐工作点约为 `394-395 Mbps` offered load，此时平均单向时延约 `3.4-4.4 ms`
- 超过 `395 Mbps` 之后，吞吐几乎不再增加，但时延会快速恶化
