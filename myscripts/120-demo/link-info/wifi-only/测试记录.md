## 追加定位（2026-04-05）

结论：`40 Mbps` 这类异常不是 `Simulator::Stop(3.0s)` 没生效，也不是 `wifiAssocStaggerMs` 之类的关联阶段参数出错；根因是这个脚本把每个 UDP 源都做成了“完全确定性”的 CBR：

- `OnOffHelper::SetConstantRate(DataRate(offeredLoad), packetSize)` 让每个源严格按固定周期发包。
- `clientStart + i * clientStartStepMs` 让每个源的初始相位也固定。
- AP beacon jitter 被关闭，当前又使用 `SpectrumWifiPhy + Friis + IdealWifiManager`，整个系统几乎没有扰动。

对 `packetSize=1400` 来说：

- `40.000 Mbps` 对应精确发包周期 `11200 / 40e6 = 280 us`
- `39.900 Mbps` 对应 `280.701754 us`
- `40.010 Mbps` 对应 `279.930017 us`
- `40.100 Mbps` 对应 `279.301746 us`

实测对照：

- `39.9 Mbps`：正常结束，`real=13.97`
- `40.0 Mbps`：`timeout 45s` 仍未结束
- `40.01 Mbps`：`timeout 35s` 仍未结束
- `40.1 Mbps`：正常结束，`real=13.74`
- `40.0 Mbps + clientStartStepMs=10.1`：正常结束，`real=13.51`
- `40.0 Mbps + wifiAssocStaggerMs=21`：仍然超时
- `40.0 Mbps + wifiSpectrumUseFriisLoss=false`：正常结束，`real=9.98`

因此问题不在“40 比 39 大 1 Mbps”，而在“`40.0/40.01` 附近的固定发包周期 + 固定初始相位 + 确定性 Wi-Fi 时序”触发了病态同步/相位锁定，导致 `3.0s` 之前的 MAC/PHY 事件数爆炸。

已在脚本里加入一个默认的、确定性的 `clientStartSkewUs=100`（每个 client 额外增加 `100 us` 启动 skew），这样仍然保持可复现，但默认不会再卡在这个精确相位点上。若要复现原始病态，可显式传：

```bash
--clientStartSkewUs=0
```
