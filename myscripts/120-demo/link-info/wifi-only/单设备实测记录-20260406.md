# 单设备实测记录（2026-04-06）

## 先看结论

这次先只看 `1` 个 Wi-Fi client、`1` 个 AP 的情况，不改代码，只运行现有脚本 `myscripts/120-demo/link-info/wifi-only/link-info-wifi-only.cc`。  
在当前默认无线参数下，单设备的 UDP 实收吞吐上限大约在 `1.90 Gbps` 左右；继续提高发送负载，吞吐基本不再上涨，只会明显抬高排队时延。  
如果同时考虑“高吞吐 + 低时延”，比较稳妥的工作点大约是 `1.85-1.87 Gbps`，此时平均单向时延约 `2.0-2.3 ms`。  
低负载时的平均单向时延基线约为 `1.08-1.15 ms`，这与脚本中固定设置的 `1 ms` AP 到 server 单向有线回程时延是一致的。

## 改动情况

本节没有修改 `ns-3`、`ns-3-dce` 或本脚本源码，只做参数扫描与结果记录。

## 测试目的

前面已经知道脚本默认每个 client 的 `offeredLoadMbpsPerClient=300`，但这只能回答“默认 300 Mbps 负载下能跑到多少”，不能直接代表单设备链路上限。  
因此本节采用“控制其他参数不变，只提高单 client offered load”的办法，观察：

- 单设备可达到的 UDP 实收吞吐上限。
- 吞吐进入平台期之前，平均单向时延大约落在哪个范围。
- 超过平台期之后，时延和丢包如何恶化。

### 参数口径补充

这里最容易误解的是 `offeredLoadMbpsPerClient` 和 `packetSize` 的口径。

- `offeredLoadMbpsPerClient` 作用在 **应用层发包器 `OnOffApplication`** 上，表示发送端按多快的速率生成“应用层包”。
- `packetSize` 表示这个“应用层包”的大小，不是 IP 层总包长，也不是 Wi-Fi MAC 帧长。
- 本脚本把 source 和 sink 的 `EnableSeqTsSizeHeader` 都打开了，所以每个应用层包里还会带一个 `SeqTsSizeHeader`，其大小固定为 `20 B`。
- 因此默认 `packetSize=1400 B` 时，真正的净业务 payload 只有 `1400 - 20 = 1380 B`。
- UDP 头、IP 头、802.11 MAC 头、PHY 前导码、ACK、竞争开销都 **不包含** 在 `packetSize` 和 `offeredLoadMbpsPerClient` 里，它们属于更低层的额外开销。

换句话说，默认参数下：

- `offeredLoadMbpsPerClient=300` 的含义是：发送端想按 `300 Mbps` 的速率发 **1400 B/包的应用层包**。
- 这 `1400 B` 里包含 `20 B` 的 `SeqTsSizeHeader` 和 `1380 B` 的净业务 payload。
- 所以如果链路不丢包，那么净 payload 吞吐的理论上限就是 `300 * 1380 / 1400 = 295.714 Mbps`，本来就会小于 `300 Mbps`。

## 指标口径说明

- “带宽”这里记录的是 **应用层实收吞吐**，不是 Wi-Fi PHY 标称速率。
- “延迟”这里记录的是 **单向应用层时延**。脚本通过 `SeqTsSizeHeader` 记录时间戳，在 sink 端按 `Simulator::Now() - header.GetTs()` 计算。
- “丢包率”不是链路层重传计数，而是根据接收端看到的序号间断，推断出的应用层丢失比例。
- 吞吐统计窗口是 `clientStart` 到 `simTime`，也就是本次的 `6 s` 活跃区间。

当前脚本已经同时输出两套吞吐指标：

- `grossThroughputMbps`：按每个收到的 **完整应用层包大小** 统计，也就是按 `header.GetSize()` 计字节。这个大小包含 `SeqTsSizeHeader`，但不包含 UDP/IP/MAC/PHY 头。
- `netPayloadThroughputMbps`：按去掉 `SeqTsSizeHeader` 之后的 **净应用层 payload** 统计，也就是按 `packet->GetSize()` 计字节。这个大小不包含 `SeqTsSizeHeader`，也不包含 UDP/IP/MAC/PHY 头。
- `aggregateThroughputMbps`：为了兼容旧日志，目前等同于 `netPayloadThroughputMbps`。
- `grossMinFlowThroughputMbps / grossMaxFlowThroughputMbps`：按完整应用层包大小统计的每流最小/最大吞吐。
- `netMinFlowThroughputMbps / netMaxFlowThroughputMbps`：按净应用层 payload 统计的每流最小/最大吞吐。

因此：

- 拿配置值 `offeredLoadMbpsPerClient` 做对比时，更应该看 `grossThroughputMbps`。
- 想看“真正业务数据传了多少”时，更应该看 `netPayloadThroughputMbps`。
- 如果 `grossThroughputMbps` 接近配置值、但 `netPayloadThroughputMbps` 更小，这不一定代表丢包；很多时候只是因为 `SeqTsSizeHeader` 被从净 payload 里扣掉了。

## 结果分析

### 1. 单设备可达到多少“带宽”？

如果把“带宽”理解为本脚本里 server 端实际收到的 UDP goodput，那么单设备上限大约是：

- `1.87-1.90 Gbps`。

这里要注意，这不是物理层标称速率，而是应用层实际收到的数据速率。  
物理层还包含前导码、ACK、竞争、聚合边界、协议头等开销，所以 goodput 一定低于 PHY 速率。

### 2. 单设备“延迟”能达到多少？

如果看低负载到中负载的平均单向时延，本场景大致是：

- 低负载基线约 `1.08-1.15 ms`。
- 高吞吐但未明显过载时约 `1.7-2.3 ms`。
- 一旦 offered load 提高到 `2000 Mbps` 及以上，平均单向时延迅速跳到 `50-60 ms`。

因此，这个场景下的单设备时延能力不能只报一个数字，而应分区间理解：

- “空闲/轻载时延”约 `1.1 ms`。
- “高吞吐可用时延”约 `2 ms`。
- “硬冲极限吞吐时延”约 `50-60 ms`。

### 3. 为什么 `2000 Mbps` 以后吞吐不涨、时延却暴涨？

这是典型的 **链路进入饱和后产生队列堆积** 的现象。

- 在 `1900 Mbps` 前后，空口还能基本跟上 offered load，所以吞吐还能继续增加，平均时延也只小幅上涨。
- 到 `2000 Mbps` 左右，单设备可用空口能力已经接近极限，新增报文无法及时发出，只能在发送队列和 MAC 队列里等待。
- 队列等待时间会直接体现在应用层单向时延中，因此时延先暴涨；而吞吐不会无限增大，因为链路服务速率已经封顶。

### 4. 单设备的“推荐工作点”

如果目标是“尽量高的吞吐，同时不把时延拖垮”，当前脚本参数下推荐把单设备 offered load 控制在：

- `1800-1900 Mbps` 附近。

这个区间里：

- 实测吞吐约 `1.77-1.87 Gbps`。
- 平均单向时延约 `2.0-2.3 ms`。
- 丢包率仍很低。

如果目标只是“冲链路极限”，可以看到约 `1.896 Gbps` 的实收吞吐；但这个结果伴随 `50-60 ms` 级别的平均单向时延，通常不适合作为“可用带宽”来引用。

## 小结

在 `myscripts/120-demo/link-info/wifi-only/link-info-wifi-only.cc` 的当前默认 Wi-Fi 参数下，`1` 个 client 的实际表现可以概括为：

- 单设备 UDP 实收吞吐上限约 `1.90 Gbps`。
- 低负载平均单向时延约 `1.1 ms`。
- 在较合理的高吞吐工作点，平均单向时延约 `2 ms`，吞吐约 `1.8+ Gbps`。
- 超过 `1.9 Gbps` 附近后，吞吐几乎不再增加，时延和丢包会快速恶化。
