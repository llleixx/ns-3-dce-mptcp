# `SIGSEGV` 排查与修复说明（2026-04-06）

## 先看结论

这次 `30` 台 Wi-Fi client 场景下出现的 `SIGSEGV`，根因不是业务脚本本身写坏了，而是 ns-3 Wi-Fi 内部 `BlockAckManager` 与 `WifiMacQueue` 之间的一次 **ACK 处理和队列过期处理竞争**。  
具体来说，某个 MPDU 在“刚收到 ACK”时又恰好跨过了 `WifiMacQueue::MaxDelay` 的过期门限，结果同一个 in-flight MPDU 被删了两次，最后在 `std::list::erase` 里崩掉。  
这次修复不是单纯“绕过崩溃”的 workaround，而是把 ACK 成功路径的语义纠正为：**既然该 MPDU 已经成功送达，就不应该再在 ACK 处理的这一刻被按过期丢弃**。  
修复后，原先会崩的 `30 台 / 20、30、50 Mbps/台` 都能正常结束；同时 `wifi-mac-queue` 和 `wifi-block-ack` 两个相关测试套件也通过。

## 一、为什么说这是一个真正的 bug

### 1. 复现现象

在以下场景中可以稳定复现崩溃：

- 单 AP
- `numClients=30`
- 默认 `wifiMuSchedulerStations=6`
- `offeredLoadMbpsPerClient=20`、`30`、`50` 等部分中高负载点

运行时症状是：

- 程序启动后能正常打印默认参数和 `STA split`
- 运行一段时间后直接 `SIGSEGV`
- 没有进入脚本自己的汇总输出

### 2. `gdb` 回溯定位

先用优化版确认大致路径，再用 debug 版拿精确源码行号。  
debug 版回溯的关键部分如下：

- `ns3::BlockAckManager::HandleInFlightMpdu(...)` at `src/wifi/model/block-ack-manager.cc:390`
- `ns3::BlockAckManager::NotifyGotAck(...)` at `src/wifi/model/block-ack-manager.cc:452`

- `HandleInFlightMpdu` 为什么会拿着一个无效 iterator 去 `erase`

- **把“崩在哪里”转换成“哪个语义动作把状态搞坏了”**

### 3. 直接崩在 `erase()`，不是“空指针乱飞”

debug 栈里最顶上是：

- `std::__detail::_List_node_base::_M_unhook()`
- `std::list<...>::erase(...)`

这类崩溃形态高度符合：

- 迭代器已经失效
- 同一个链表节点被重复摘链

因此第一轮假设就不是“某个对象为 null”，而是：

- **链表元素被重复删除**

这个判断很关键，因为它直接决定了后面读代码的方式。

## 二、根因是怎么一步步缩小出来的

### 1. 从崩溃点往前倒推

崩溃点在 `BlockAckManager::HandleInFlightMpdu()` 的 `ACKNOWLEDGED` 分支：

```cpp
if (status == ACKNOWLEDGED)
  {
    m_queue->DequeueIfQueued (*mpduIt);
    return it->second.second.erase (mpduIt);
  }
```

这段逻辑的语义是：

1. 先把 MPDU 从 EDCA 队列里 dequeue
2. 再把同一个 MPDU 从 Block Ack 的 in-flight list 里 erase

如果这里崩了，最自然的问题就是：

- 在 `DequeueIfQueued()` 期间，有没有可能又回调回 `BlockAckManager`，把同一个 `mpduIt` 提前删掉？

### 2. 顺着 `DequeueIfQueued()` 往下看

`WifiMacQueue::DequeueIfQueued()` 最终会进 `DoDequeue()`。  
而 `DoDequeue()` 在真正 dequeue 之前，会先做一次：

```cpp
if (TtlExceeded (pos, Simulator::Now ()))
  {
    return nullptr;
  }
```

`TtlExceeded()` 的行为不是单纯返回 `true/false`，它会：

1. 执行 `DoRemove(curr)`
2. 触发 `Expired` trace

也就是说，这里不是“安静地发现过期”，而是会**主动删除队列项并触发回调**。

### 3. 再看 `Expired` trace 接到了哪里

`QosTxop` 在初始化时把 `WifiMacQueue` 的 `Expired` trace 接到了：

- `BlockAckManager::NotifyDiscardedMpdu`

这就形成了一条重入链：

1. `HandleInFlightMpdu(... ACKNOWLEDGED ...)`
2. 调 `m_queue->DequeueIfQueued(*mpduIt)`
3. `DoDequeue()` 发现 TTL 已过
4. `TtlExceeded()` 触发 `Expired`
5. `Expired -> BlockAckManager::NotifyDiscardedMpdu()`
6. `NotifyDiscardedMpdu()` 又把这个 MPDU 从 in-flight list 里删掉
7. 控制流返回 `HandleInFlightMpdu()`
8. 原代码继续 `erase(mpduIt)`，第二次删同一个节点
9. `SIGSEGV`

这时整个因果链已经闭合了。

### 4. 为什么这个 bug 在多设备场景更容易撞上

单设备时：

- 排队等待时间短
- ACK 往往在生命周期窗口内就到了

`30` 台时：

- 调度等待时间显著变长
- MPDU 更容易在“已经发出去、正在等 ACK”的这段时间里跨过 `MaxDelay`

因此，多用户高负载场景不是“制造了另一个 bug”，而是把这个原本潜伏的竞争窗口大幅放大了。

## 三、为什么这次修复是合理的，而不是 workaround

### 1. 修复的核心语义

修复后，`ACKNOWLEDGED` 路径改成：

```cpp
m_queue->DequeueIfQueued (*mpduIt, true);
return it->second.second.erase (mpduIt);
```

这里新增了一个 `ignoreExpired=true` 的分支，意思是：

- **在 ACK 成功路径上，从队列里正常 dequeue 这个 MPDU，但不要在这一刻再次做 TTL 过期判定**

这不是“把崩溃藏起来”，而是在修正状态机语义：

- 这个 MPDU 已经被成功接收并被 ACK 了
- 它应该被视为“成功送达并出队”
- 不应该在 ACK 处理的同一时刻又被视为“因在队列里待太久而丢弃”

### 2. 它保留了正确的 queue 行为，而不是硬跳过逻辑

如果只是为了不崩，最粗暴的做法可以是：

- 在 ACK 路径里直接 `erase(mpduIt)`，完全不碰队列
- 或者把 `erase` 外面包一层 if/try 式防护

这些都属于真正的 workaround，因为它们不能保证队列状态、统计和 trace 仍然一致。  

我没有这么做，而是：

- 仍然调用 `DequeueIfQueued()`
- 仍然走 `DoDequeue()` 的正常 dequeue 统计和 trace
- 只是禁止它在 ACK 成功这一刻重新跑过期删除回调

因此，修复后的行为仍然是：

- 这是一次“成功 dequeue”
- 不是一次“drop after dequeue”

这一点很重要，因为如果错误地改成 `Remove()`，ns-3 的 queue 统计会把这次成功发送记成 drop，这会引入新的语义错误。

### 3. 这个方向与本地 ns-3 历史是相符的

本地 `ns-3.35` 历史里有一条提交：

- `edcd9a6909bdf12ea837913bdcb6b4c5936c6a67`
- 标题：`wifi: Cleanup WifiMacQueue`

提交说明里明确写到：

- MPDU 过期已经会在专门的路径里处理
- 在“每次 packet dequeue”时都检查过期是多余的
- 而且 **sometimes troublesome**

也就是说，ns-3 自己的历史意图本来就是：

- 过期处理应集中在专门位置
- dequeue 路径里重复触发过期逻辑，容易出问题

这次修复并没有违背原始设计，反而是把 ACK 路径收敛回这种设计意图。

### 4. 为什么不把改动扩大到所有 dequeue 路径

这里有一个工程判断：

- `DequeueIfQueued()` 不是只在 ACK 成功路径里调用
- 例如 A-MSDU 聚合、普通 `FrameExchangeManager::DequeueMpdu()` 也会调用它

如果直接把所有 dequeue 都改成“永远忽略 TTL”，改动面会更大，也更容易引入未验证的副作用。  

当前崩溃明确只发生在：

- 成功收到 ACK
- 仍然维护 in-flight list 的 Block Ack 路径

因此本次修复是：

- **改变最小**
- **语义最明确**
- **直接命中根因**

这比“把整个队列的过期策略一股脑改掉”更稳妥。

## 六、我是怎么快速把这个 bug 找出来的

这一部分更偏“方法”。

### 方法 1：先把问题归类，而不是先猜代码

一看到崩溃位置是：

- `std::list::_M_unhook`
- `std::list::erase`

我先做的不是到处搜 null，而是立刻把问题归类为：

- 失效迭代器
- 双删
- 容器重入修改

这一步会极大减少无效搜索。

### 方法 2：先用 opt 复现路径，再用 debug 取精确行号

优化版更容易快速复现大场景问题；  
debug 版更容易拿到精确代码位置。  

所以我采用的是：

1. opt 下先确认稳定复现
2. gdb 拿到函数级回溯
3. debug 下再跑一次，拿源码行号

这比一开始就在 debug 下盲跑大场景更高效。

### 方法 3：从崩溃点往回看“谁会重入”

当崩溃发生在：

- `erase(mpduIt)`

我会立刻问：

- 在这句前面，谁可能间接修改了同一个容器？

然后顺着调用链看：

- `HandleInFlightMpdu`
- `DequeueIfQueued`
- `TtlExceeded`
- `Expired` trace
- `NotifyDiscardedMpdu`

这样就能把“间接修改同一容器”的路径快速闭合出来。

### 方法 4：优先找“状态机冲突”，不是只找“哪一行错了”

真正的问题不是“390 行错了”，而是：

- 同一个 MPDU 在同一时刻被两个状态机同时认领
- 一个状态机说“ACK 成功，应成功出队”
- 另一个状态机说“TTL 已过，应按过期丢弃”

只要你能把这两个 competing state 识别出来，修复思路就会自然很多。

### 方法 5：修复时先想“正确语义是什么”

我修之前先判断：

- ACK 成功时，到底应该记成成功发送还是过期丢弃？

如果这个问题没想清楚，就很容易做出“虽然不崩，但语义错了”的补丁。  

这里正确语义显然是：

- 已经收到 ACK，就应当视为成功送达

所以修复必须保留 dequeue 语义，而不是粗暴改成 remove/drop。

### 方法 6：验证时分三层

我通常把验证拆成三层：

1. **场景复现**：原来的 crash 点是否消失
2. **相关模块测试**：有没有把附近逻辑打坏
3. **定向回归测试**：能不能把这次 bug 的触发条件锁住

这次三个层次都做了，所以我对修复合理性是有把握的。

## 七、如果你想练这种 debug 能力，可以刻意训练什么

### 1. 学会从崩溃形态反推 bug 类型

看到这些词要立刻建立联想：

- `erase` / `_M_unhook`：优先想双删、失效迭代器
- `unordered_map` rehash 附近崩：优先想引用/迭代器失效
- `pure virtual method called`：优先想析构期回调
- `double free`：优先想 ownership 冲突

### 2. 先抓一条“可操作”的回溯

不要一开始就靠读代码猜。  
哪怕只是：

- `gdb -batch -ex run -ex bt --args ...`

也足够把问题从“全项目搜索”缩到“一两个函数”。

### 3. 读代码时盯住容器、回调、生命周期

排崩溃最值钱的三个关键词是：

- 谁拥有这个对象
- 谁还能回调回来
- 谁会改这个容器

很多复杂 bug 最后都落在这三件事上。

### 4. 修复前先写出“不变式”

比如这次的不变式可以写成：

- 一个 in-flight MPDU 在 ACK 成功处理期间，最多只能被从 in-flight list 删除一次
- ACK 成功路径不能把成功送达的 MPDU记成 Expired drop

只要你能先把不变式说清楚，补丁就不容易跑偏。

## 八、小结

这次 `SIGSEGV` 的定位过程，本质上不是“灵感很好”，而是遵循了一个比较稳定的调试流程：

1. 先复现
2. 用 `gdb` 把范围压到具体函数
3. 根据崩溃形态判断 bug 类型
4. 沿调用链寻找重入和共享容器修改
5. 用状态机语义判断什么才是正确修复
6. 用场景 + 单测 + 回归测试三层验证修复

如果你以后也按这个顺序练，debug 速度会明显提升。  
真正能拉开差距的，通常不是“记住了多少 API”，而是你能不能快速把一个 bug 变成：

- 一个具体的失效不变式
- 一条闭合的因果链
- 一个被验证过的最小修复
