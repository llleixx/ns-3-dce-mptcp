# Wi-Fi 关联状态机排查与修复说明（2026-04-07）

## 先看结论

这次暴露出来的问题不是 `link-info-wifi-only.cc` 脚本本身“不能没有 `wifiAssocStaggerMs`”，而是 ns-3 Wi-Fi 的 AP（Access Point，接入点）侧关联状态机里有一个实现 bug。  
当多个 STA（Station，无线终端）几乎同时关联时，某个 STA 的 Association Response（关联响应）可能先触发一次 `MpduResponseTimeout`，但随后又在重传后真正收到 ACK（Acknowledgment，确认应答）。  
旧实现把前面的 timeout 直接当成“最终失败”，过早把 AP 侧 station manager 状态打成未关联；而后面的 ACK 成功又不会把状态救回来，于是 AP 内部出现“`m_staList` 里有这个 STA，但 `IsAssociated()` 为假”的不一致。  
这次修复的核心不是“重新把 `wifiAssocStaggerMs` 加回来”，而是把 AP 侧状态更新时机改成与 MAC 实际语义一致：**只有真正 ACK 成功才完成关联；只有真正达到重传上限被丢弃，才判定关联失败**。  
修复后，取消 `wifiAssocStaggerMs` 仍然可以在 `30` 台场景下跑出 `activeFlows=30/30`；同时已有的 `wifi-devices` 和 `wifi-primary-channels` 测试套件也通过，因此这个修复不是临时 workaround。

## 一、改动说明

### 1. 局部改动

本次保留在业务脚本里的局部改动只有一项：

- 从 [link-info-wifi-only.cc](/root/bake/source/ns-3-dce/myscripts/120-demo/link-info/wifi-only/link-info-wifi-only.cc) 中删除了 `wifiAssocStaggerMs` 及其对 `StaWifiMac::WaitBeaconTimeout` 的覆盖。

具体含义是：

- 每个 STA 不再使用 `120 ms + i * wifiAssocStaggerMs` 的递增等待时间。
- `StaWifiMac` 回退到 ns-3 默认的 `WaitBeaconTimeout = 120 ms`。
- 这样所有 STA 在被动扫描（passive scanning）结束后，会更接近同时发起首次 Association Request（关联请求）。

这个改动的落点在：

- [link-info-wifi-only.cc](/root/bake/source/ns-3-dce/myscripts/120-demo/link-info/wifi-only/link-info-wifi-only.cc#L226)

### 2. 全局改动

真正的 bug 修复发生在 ns-3 Wi-Fi 内部，涉及：

- [ap-wifi-mac.h](/root/bake/source/ns-3.35/src/wifi/model/ap-wifi-mac.h)
- [ap-wifi-mac.cc](/root/bake/source/ns-3.35/src/wifi/model/ap-wifi-mac.cc)

修复后的核心行为是：

- AP 不再把 `MpduResponseTimeout` 直接当作 Association Response 的最终失败。
- AP 改为监听 `DroppedMpdu`，只在 MPDU 真正达到重传上限（retry limit）被丢弃时，才把这次关联判定为失败。
- AP 在发送成功状态的 Association Response 时，只先记录一份 pending（待完成）关联信息；只有在 `AckedMpdu` 到来时，才真正完成关联。
- 如果最终失败，就回滚这份 pending 关联，避免 `m_staList`、AID（Association ID，关联标识）和 station manager 的状态分叉。

## 二、为什么说这是一个真正的实现 bug

### 1. 问题现象

在 `30` 台、单 AP、取消 `wifiAssocStaggerMs` 的场景下，原来能稳定复现：

- 某个 STA 自己认为已经关联成功；
- AP 的 `m_staList` 里也已经有它；
- 但 AP 侧 `WifiRemoteStationManager::IsAssociated()` 却返回假；
- 于是这个 STA 后续发来的 ARP（Address Resolution Protocol，地址解析协议）请求会被 AP 丢弃，最终表现为 `activeFlows < 30`。

这不是正常的“无线链路偶尔丢包”，而是 AP 内部两个状态来源彼此矛盾：

- `m_staList` 表示“AP 维护的已关联 STA 列表”
- `WifiRemoteStationManager::IsAssociated()` 表示“AP 在转发上行数据时认不认这个 STA”

同一个 STA 同时满足“在列表里”和“不被 AP 当成已关联”，就是状态机实现错误。

### 2. 直接证据链

这次排查抓到的关键序列是：

1. AP 给某个 STA 发送 Association Response。
2. 同一个 MPDU 先触发一次 `MpduResponseTimeout`。
3. 随后，同一个 STA 的 Association Response 又真正收到了 ACK。
4. STA 端进入 `Associated`。
5. AP 侧却仍然把它当成 `IsAssociated() == false`。

这条证据链说明：

- `MpduResponseTimeout` 只能说明“这次超时前没收到响应”，不能说明“最终一定失败”。
- 但旧代码正是在 timeout 发生时，直接调用 `RecordGotAssocTxFailed()`，把 AP 侧状态改成了失败。
- 之后即使 `AckedMpdu` 到来，`TxOk()` 也不会再把这个 STA 正确恢复为已关联，因为它只处理 `WAIT_ASSOC_TX_OK` 状态。

### 3. 相关概念解释

#### 3.1 `WaitBeaconTimeout`

- 定义：STA 在被动扫描时，等待 beacon（信标）的超时时间。
- 单位：毫秒（ms）。
- 影响方向：值越大，STA 发起首次关联请求的时间通常越晚；不同 STA 若取不同值，就能把关联请求主动错开。
- 本次为什么相关：取消 `wifiAssocStaggerMs` 后，30 个 STA 都回到默认 `120 ms`，关联请求更容易挤在一起，从而把 AP 侧状态机 bug 稳定放大出来。

#### 3.2 `MpduResponseTimeout`

- MPDU（MAC Protocol Data Unit，MAC 协议数据单元）是 802.11 MAC 层发送和确认的基本单位。
- `MpduResponseTimeout` 的含义是：当前这次发送在超时前没有收到应答。
- 它不是“最终失败”的同义词，因为 MAC 层还可能继续重传，后续仍然成功。

#### 3.3 `DroppedMpdu`

- `DroppedMpdu` 表示这个 MPDU 已经被 MAC 真正丢弃。
- 其中 `WIFI_MAC_DROP_REACHED_RETRY_LIMIT` 的含义是：重传已经达到上限，MAC 决定放弃。
- 这才是“最终失败”的合适判据。

#### 3.4 `AckedMpdu`

- `AckedMpdu` 表示这个 MPDU 已经成功收到对端确认。
- 对 Association Response 来说，它才是“AP 可以正式把 STA 视为已关联”的可靠信号。

#### 3.5 AID 和 `m_staList`

- AID（Association ID）是 AP 分配给 STA 的关联编号。
- `m_staList` 保存的是 `(AID, MAC 地址)` 映射。
- 如果 AP 在响应刚发出去时就把 STA 提前塞进 `m_staList`，而后面又没等真正 ACK 成功，就会有机会出现“表里有、但逻辑上没关联成功”的状态不一致。

## 三、根因定位

旧实现的问题集中在两点。

### 1. 失败信号选错了

旧代码在 AP 初始化时，把：

- `AckedMpdu` 连接到 `ApWifiMac::TxOk()`
- `MpduResponseTimeout` 连接到 `ApWifiMac::TxFailed()`

也就是说，旧逻辑把“超时”当成了“失败完成”。  
但从 `RegularWifiMac` 的 trace 语义看，`MpduResponseTimeout` 只表示这一次没在时限内收到响应；真正的最终失败应当看 `DroppedMpdu` 和具体 drop reason（丢弃原因）。

### 2. 成功状态提交得太早

旧 `SendAssocResp()` 的做法是：

- 在成功响应入队前，就把 STA 插入 `m_staList`
- 同时触发 `AssociatedSta` trace
- 还设置了 AID

但 station manager 真正变成 `GOT_ASSOC_TX_OK` 却要等到 `TxOk()`，也就是等 ACK 到来之后。  
这样一来，只要中间先被 timeout 抢先改成失败，就会形成两套状态分叉：

- `m_staList` 已包含这个 STA
- station manager 却认为它不在 `GOT_ASSOC_TX_OK`

AP 处理上行数据时使用的是后者，因此这个 STA 的数据和 ARP 会被丢掉。

## 四、为什么当前修复是合理的，而不是 workaround

### 1. 修复遵守 MAC 语义

这次修复没有引入“额外延时”“特殊重试次数”“给某个 STA 开后门”这类场景特化逻辑。  
修复做的事情是把事件语义对齐：

- `AckedMpdu` 才表示成功
- `DroppedMpdu + REACHED_RETRY_LIMIT` 才表示最终失败

这和 802.11 MAC 的真实发送生命周期是一致的。

### 2. 修复消除了内部状态分叉

当前实现把 Association Response 的成功提交拆成两步：

1. 先保存 pending 关联信息
2. 等 ACK 到来后再 finalize

这样做的好处是：

- AP 的 `m_staList`
- AID
- `AssociatedSta` trace
- station manager 的 `GOT_ASSOC_TX_OK`

会在同一个“真正成功”的时刻完成提交，而不是前后分裂。

### 3. 对 reassociation 也保持语义正确

如果一个已关联 STA 做 reassociation（重新关联），而这次响应最终失败，当前修复会保留原先那个已经确认过的关联状态，而不是把它错误打成完全未关联。  
这也是更符合直觉和协议语义的行为。

## 六、为什么取消 `wifiAssocStaggerMs` 后才更容易暴露这个 bug

`wifiAssocStaggerMs` 的作用是把每个 STA 的 `WaitBeaconTimeout` 做线性错开。  
在旧脚本里，关联请求的大致起始时刻会变成：

- `120 ms`
- `140 ms`
- `160 ms`
- ...

这样做的效果是：

- 同一 AP 下的 Association Request 不会高度重叠
- AP 的 Association Response 也不太容易在相近时刻一起进入“先 timeout、后重传成功”的边界条件

一旦去掉这个错峰：

- 30 个 STA 都更接近在 `120 ms` 左右启动关联
- 无线控制帧竞争显著增大
- AP 状态机里的这个竞态就更容易被稳定命中

所以：

- `wifiAssocStaggerMs` 原来确实能“掩盖”这个 bug
- 但它不是根因修复
- 真正该修的是 AP 侧关联状态机的事件判定与提交时机

## 七、本次小结

这次问题的本质不是“30 台一定需要人为错峰关联”，而是：

- AP 把 `MpduResponseTimeout` 误判成了最终失败；
- 同时又过早提交了 `m_staList` 和 AID；
- 导致 AP 内部出现“列表里有 STA，但 station manager 不承认”的不一致；
- 进而把该 STA 的 ARP 和上行数据丢掉。

修复后：

- 关联成功只在真正收到 ACK 时提交；
- 最终失败只在真正达到 retry limit 时判定；
- `wifiAssocStaggerMs` 即使取消，`30` 台场景也能恢复到 `activeFlows=30/30`。

因此，这次修复是一个**语义对齐的状态机修复**，不是单纯为了让当前脚本跑通而增加的 workaround。
