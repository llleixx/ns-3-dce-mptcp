# 120-demo 当前结论

日期：`2026-04-05`

## 结论

当前问题可以分成两层：

1. **真实的高负载性能问题**
   `120-demo` 在 `single AP + 100 Mbps/client + MPTCP + WiFi` 这个参数区间，确实存在明显的复杂度阈值效应。客户端数从 `6` 增加到 `9` 后，墙钟时间会陡增，debug 版尤其明显。

2. **额外的环境敏感问题**
   同一条命令在部分运行环境下，墙钟时间会进一步变化。这个环境敏感问题已经确认存在，但它**不是**当前高负载变慢现象的唯一原因，也还**不能**直接下结论说一定是未定义行为（Undefined Behavior, UB）。

因此，当前更稳妥的判断是：

- `9 clients / 100 Mbps` 的“很慢”首先是**真实热点**导致的；
- 启动环境还会在这个基础上放大或缩小墙钟时间；
- debug 版已经足够说明：即使不考虑环境敏感项，这个参数点本身也已经处在非常差的性能区间。

### 1. optimized 版

#### `6 clients / 1 AP / 3 s / 100 Mbps / OFDMA off`

- 慢环境：`real=26.06 s`
- 观测：
  - `nrActive=6/6`
  - `wifiActive=6/6`

#### `9 clients / 1 AP / 3 s / 100 Mbps / OFDMA off`

- 在“快环境”下大约 `42 s` 到 `50 s`
- 在“慢环境”下可以长时间跑不完
- 观测：
  - `nrActive=9/9`
  - `wifiActive` 常见不是 `9/9`

### 2. debug 版

#### `6 clients / 1 AP / 3 s / 100 Mbps / OFDMA off`

- 快环境：`real=130.81 s`
- 慢环境：`real=122.15 s`
- 观测：
  - 两组都不是稳定的 `wifiActive=6/6`
  - 一组缺 `UE 3`
  - 一组缺 `UE 0`

这说明 debug 版下：

- 运行环境差异仍然存在，但没有 optimized 版那么主导；
- 更明显的是，当前场景本身存在**时序敏感/边缘不稳定**问题。

#### `9 clients / 1 AP / 3 s / 100 Mbps / OFDMA off`

- 你本地测试结果：**半小时都跑不完**
- 这已经足以说明：debug 版下 `9 clients` 进入了不适合作为常规调试基线的高开销区间。

## 当前最可信的判断

### 已经基本确定的部分

- `9 clients / 100 Mbps` 不是简单的“命令打错了”。
- debug 版和 optimized 版都说明：`6 -> 9 clients` 会触发非常明显的墙钟恶化。
- 当前代码里存在“哪个 UE 没有 WiFi payload 会漂移”的现象，这更像**时序敏感问题**，而不是一个固定节点、固定条件下必现的单点逻辑错误。
- optimized 版里，“快环境 / 慢环境”差异会明显改变 wall-clock。
- debug 版里，这种环境差异仍然存在，但不像 optimized 版那样主导；debug 版主导现象仍然是高负载本身的复杂度爆炸。

### 还不能下死结论的部分

- 还不能说“这一定是未定义行为”。
- 也还不能说“最近为了调试加的脚本/trace 改动引入了这个问题”。

## 建议的使用方式

在继续排查逻辑正确性时，建议：

1. **正确性调试**优先用 `6 clients`
   因为 `9 clients` 在 debug 版已经过慢。
2. **性能/阈值分析**再单独看 `9 clients`
   不要把两类问题混在一起。

## 一句话总结

当前最稳妥的结论是：

> `120-demo` 在 `9 clients / 100 Mbps` 时，已经存在真实的高负载性能爆炸；  
> 同时还伴随一个会改变墙钟时间和“缺失 WiFi payload UE”的环境/时序敏感问题；  
> 但现阶段还不能把它直接定性成“已经确认的未定义行为”。
