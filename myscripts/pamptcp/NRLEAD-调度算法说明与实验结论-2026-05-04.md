# NRLEAD 调度算法说明与实验结论

日期：2026-05-04  
实现位置：`/root/bake/source/net-next-nuse-mptcp-0.92/net/mptcp/mptcp_nrlead.c`  
实验脚本：`myscripts/pamptcp/pamptcp.cc`

## 1. 结论

`nrlead` 的核心结论是：P3 peak 不能再沿用 default 的“哪个子流可用、RTT 低就发哪个”思路；应该让 Wi-Fi 先承载主体数据，再让 NR 以小块、限速、受保护的方式做 tail assist。最终版本在 `p3-sub-peak-8` 中让 P3 peak 的 NR share 达到 `1.213%`，明显高于 `nrsafe` 的 `0.408%` 和 `testprio` 的 `0%`，同时 steady delay 的 p99/max 为 `6.241/6.489 ms`，没有超过 10 ms。对 peak 流量，`nrlead` 在 `p3-sub-peak-8` 的 peak p99 为 `391.626 ms`，优于 `testprio` 的 `468.806 ms` 和 `nrsafe` 的 `997.672 ms`。这说明问题不只是“NR 给多少”，而是“什么时候给、按什么节奏给、是否会撞到 steady 小包”。

## 2. 背景与问题

MPTCP（Multipath TCP，多路径 TCP）会把一个应用层 TCP 连接拆成多条 subflow（子流）。在本实验里，每个 UE（User Equipment，用户设备）同时具备 NR（New Radio，5G 新空口）和 Wi-Fi 两条上行路径，scheduler（发送调度器）负责决定每个待发送数据片段走哪条 subflow。

场景里有三类流量：

- P1 steady：优先级最高，小速率周期流。
- P2 steady：中优先级，小速率周期流。
- P3 steady/peak：P3 平时也有 steady 小流量，部分场景中有大突发 peak。

目标不是单纯让 peak 更快，而是在 peak 使用一部分 NR 的同时，不明显伤害 steady 流量，尤其希望 steady 的尾部时延控制在 10 ms 内。

旧的 `nrsafe` 方向可以保护 steady，但 P3 peak 的 NR 使用比例太低。它的问题不只是参数保守，而是根本策略仍然接近“default 先选路，选到 NR 后再判断是否拦截”。这种策略容易让 NR 承载早期低序号数据。一旦 Wi-Fi 后续数据先到，MPTCP 接收端仍要按数据序号交付给应用，就会产生 HoL（Head-of-Line blocking，队首阻塞）。

## 3. NRLEAD 的设计思路

`nrlead` 的全称可以理解为 “Wi-Fi-led NR tail assist”。含义是：P3 peak 由 Wi-Fi 领先发送，NR 只在 Wi-Fi 已经发送了一段数据后参与后续小块数据的辅助发送。

整体策略分三层：

1. steady 流量优先走 NR。
2. P3 peak 默认走 Wi-Fi。
3. P3 peak 只有满足 Wi-Fi lead、NR clean、share budget、token bucket 等条件时，才允许 NR assist。

这里的 tail assist 不是修改 MPTCP 写队列去显式取“最后一个 skb（socket buffer，套接字缓冲区）”，而是通过“Wi-Fi 已经发送足够多 peak 字节后才解锁 NR”的方式，让 NR 承载更靠后的序号区间。这样可以减少 NR 承载关键低序号片段导致的 HoL 风险。

## 4. 调度流程

### 4.1 steady 流量

如果当前连接不是 P3 peak，`nrlead` 会优先选择 NR subflow：

```text
非 P3 peak -> 优先 NR -> NR 不可用时 fallback 到 default 可用路径
```

这样做的原因是当前任务设定中 steady 可以先固定走 NR。NR 的容量不一定最大，但在本场景中它对小包更稳定，能避开 Wi-Fi 多 UE 竞争带来的随机尾部。

### 4.2 P3 peak 流量

P3 peak 的主路径是 Wi-Fi：

```text
P3 peak -> 默认 Wi-Fi
        -> 若 Wi-Fi 已经领先、Wi-Fi 有压力、NR 干净、预算允许
        -> NR 发送一个小块 assist
```

这里的“Wi-Fi lead”是算法的关键。只有同一条 MPTCP 连接已经通过 Wi-Fi 发出至少 `512 KiB` peak 数据后，NR 才有资格参与。这样避免 peak 刚开始时 NR 抢到低序号数据。

### 4.3 NR assist 的准入条件

P3 peak 使用 NR 必须同时满足：

- 当前流量被识别为 P3 peak。
- 同一连接 Wi-Fi peak 发送量已经超过 `wifi_lead_bytes`。
- Wi-Fi 有压力，例如 queue delay 超过阈值或 CWND（Congestion Window，拥塞窗口）占用较高。
- NR 当前足够 clean，例如 RTT（Round-Trip Time，往返时延）膨胀、队列估计、CWND 占用没有越界。
- 单连接和全局 NR share 没有超过预算。
- 全局 token bucket 里还有 NR assist credit。
- 单次 assist 大小不超过 `16 KiB`。

## 5. 关键参数

| 参数 | 当前值 | 单位 | 作用 | 变大/变小的影响 |
|---|---:|---|---|---|
| `peak_backlog_bytes` | `64 KiB` | Byte | 判断当前连接是否像 peak 流 | 变小会更早把连接识别为 peak；变大可能漏掉短突发 |
| `wifi_lead_bytes` | `512 KiB` | Byte | Wi-Fi 领先多少后才允许 NR assist | 变大更保护 steady 和 HoL，但 NR share 降低；变小 NR 更早参与，风险更高 |
| `nr_peak_share_pct` | `8%` | 百分比 | 单连接 P3 peak 的 NR share 上限 | 变大允许更多 NR assist；过大可能伤 steady |
| `global_nr_peak_share_pct` | `8%` | 百分比 | 全局 P3 peak 的 NR share 上限 | 限制所有 peak 合计占用 NR 的比例 |
| `nr_assist_chunk_bytes` | `16 KiB` | Byte | 单次 NR assist 最大块大小 | 变大提升 NR 瞬时参与度，但更容易造成排队和 HoL |
| `global_nr_assist_cap_bytes` | `16 KiB` | Byte | 全局 NR assist token bucket 容量 | 变大允许多个 peak 近乎同时冲进 NR；本实验中 `48 KiB` 会导致 P2 尾部变差 |
| `global_nr_assist_refill_bytes_per_sec` | `1536 KiB/s` | Byte/s | 全局 NR assist token bucket 恢复速率 | 变大提升长期 NR share；变小更保护 steady |
| `wifi_pressure_queue_us` | `3000 us` | 微秒 | Wi-Fi queue delay 超过该值才认为 Wi-Fi 有压力 | 变小 NR 更容易 assist；变大更保守 |
| `wifi_pressure_cwnd_pct` | `70%` | 百分比 | Wi-Fi CWND 占用超过该值认为有压力 | 变小更容易触发 NR assist |
| `nr_queue_guard_us` | `5000 us` | 微秒 | NR queue delay 上限 | 变大 NR 更容易参与；变小更保护 steady |
| `nr_rtt_guard_us` | `5000 us` | 微秒 | NR RTT 相对 min RTT 的绝对膨胀上限 | 防止 NR 已经拥塞时继续接 peak |
| `nr_rtt_guard_pct` | `80%` | 百分比 | NR RTT 相对 min RTT 的比例膨胀上限 | 与绝对阈值取更宽松者 |
| `nr_cwnd_guard_pct` | `95%` | 百分比 | NR CWND 占用上限 | 接近满窗口时禁止 NR assist |
| `nr_delay_budget_us` | `10000 us` | 微秒 | 预测 NR 发送代价上限 | 与 10 ms steady 目标一致 |
| `nr_delay_slack_us` | `4500 us` | 微秒 | NR 预测代价相对 min RTT 的额外 slack | 限制 NR 从 clean baseline 偏离太多 |
| `nr_vs_wifi_slack_us` | `3000 us` | 微秒 | NR 预测代价最多比 Wi-Fi 高多少 | 避免为了分流而选择明显更慢的 NR |

参数落点均在 `mptcp_nrlead.c` 的 module parameter 区域，可通过内核模块参数形式覆盖；本实验使用代码默认值。

## 6. 为什么最终选择 token bucket

实验中间版本曾经只用总 share 限制 NR assist。它在 `p3-sub-peak-8` 中能让 P3 NR share 到约 `1.0%`，peak p99 也明显改善，但 P2 steady p99 会出现约 `17 ms` 的尾部。这说明问题不是长期 NR 使用总量过大，而是多个 peak 在相近时间点同时拿到 NR assist，和 P2 周期小包撞到一起。

最终版加入 global token bucket（全局令牌桶）。token bucket 是一种限速机制：bucket 中有 token 才允许发送，发送会消耗 token，token 按固定速率恢复。这里它的作用是限制“瞬时 NR assist 并发”，不是简单减少总流量。最终把 bucket cap 收紧到 `16 KiB` 后，`p3-sub-peak-8` 的 steady max 从中间版本的约 `15.98 ms` 降到 `6.489 ms`，同时 P3 NR share 仍保持 `1.213%`。

## 9. 结果分析

### 9.1 `p3-sub-peak-0`

`nrlead` 与 `nrsafe` 基本一致，steady 流量几乎全部走 NR。它不如 `default` 的 steady delay，是因为本任务当前明确先接受“steady 固定 NR”的设定，且文档中也说明 `p3-sub-peak-0` 不是主要优化目标。

### 9.2 `p3-sub-peak-4`

`nrlead` 的 P3 NR share 为 `1.221%`，高于 `nrsafe` 的 `0.654%` 和 `testprio` 的 `0%`。steady p99/max 保持在 `6.354/6.490 ms`，没有超过 10 ms。peak p99 为 `224.895 ms`，略好于 `nrsafe` 的 `228.972 ms` 和 `testprio` 的 `233.766 ms`。

这里说明：在中等 peak 压力下，Wi-Fi-led tail assist 可以让 NR 有更多参与，同时不明显牺牲 steady。

### 9.3 `p3-sub-peak-8`

这是最关键场景。`default` 和 `blest` 都让 P3 有约 `22%` NR share，但 steady p99 接近 `18 ms`，说明 NR 被 peak 明显污染。`nrsafe` 能保护 steady，但 P3 NR share 只有 `0.408%`，peak p99 高达 `997.672 ms`。`testprio` 完全不给 P3 使用 NR，steady 很稳，但 peak p99 为 `468.806 ms`。

`nrlead` 在该场景中取得了更好的折中：

- P3 NR share：`1.213%`
- steady p99/max：`6.241/6.489 ms`
- P2 steady p99：`5.239 ms`
- peak mean/p99：`251.002/391.626 ms`

也就是说，`nrlead` 让 P3 peak 真正拿到了一部分 NR，同时 peak p99 优于 `testprio`，steady max 仍低于 10 ms。

## 10. 最终判断

`nrlead` 比 `nrsafe` 更好的地方不是“阈值更松”，而是改变了 peak 使用 NR 的时序结构。`nrsafe` 主要限制 NR 是否 clean；`nrlead` 额外要求 Wi-Fi 先领先，并用全局 token bucket 控制 NR assist 的瞬时并发。这个机制解决了两个核心问题：

1. 减少 NR 承载低序号 peak 数据导致的 MPTCP HoL 风险。
2. 避免多个 P3 peak 同时冲进 NR，撞到 P1/P2 steady 小包。

因此，当前实验下推荐使用 `nrlead` 作为新算法：它在 `p3-sub-peak-4` 和 `p3-sub-peak-8` 都实现了可观的 P3 NR 分流，并且 steady delay 的 p99/max 均控制在 10 ms 内。
