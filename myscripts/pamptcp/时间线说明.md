# pamptcp 时间线说明

## 1. 本文范围

本文记录的是当前 `myscripts/pamptcp/pamptcp.cc` 这一版代码的时间线。

本文默认讨论两层配置：

1. `pamptcp.cc` 自带的全局默认值。
2. `myscripts/pamptcp/flow-priority-30/avg-only/` 这个 traffic profile 在“不额外传 CLI 覆盖参数”时的实际生效值。

其中第 2 层很重要，因为一旦传入 `--trafficProfileDir=...`，`templates.csv`/`groups.csv` 会覆盖每个 client 的业务参数，并把 `numClients` 改成场景文件里定义的值。

## 2. 本次代码状态

本文基于当前代码状态，包含两处已经修复的统计问题：

1. `accepted_sockets` 不再在 `Simulator::Run()` 结束后读取，而是在 `simTime - 1ns` 先做快照。否则 `PacketSink::StopApplication()` 会先把 accepted socket 列表清空，最后读到的总是 `0`。
2. server 骨干口的 payload 统计已经按 `PointToPointNetDevice` 的 PPP 封装解析，而不是旧版 `CsmaNetDevice` 的以太网帧解析。否则 `nr_payload_bytes` / `wifi_payload_bytes` 会被统计成 `0`。

## 3. 两层默认值

### 3.1 `pamptcp.cc` 全局默认值

这些值来自 `pamptcp.cc` 里 `main()` 开头的默认参数：

| 参数 | 含义 | 默认值 |
| --- | --- | --- |
| `numClients` | UE 数量 | `120` |
| `simTime` | 仿真主时长 | `20.0 s` |
| `sinkStart` | server 端 `PacketSink` 启动时间 | `1.0 s` |
| `clientStart` | client app 启动基准时间 | `2.0 s` |
| `clientStartJitter` | 每个 client 额外启动抖动范围 | `0 s` |
| `clientStartJitterStream` | 上述抖动的 RNG stream | `1` |
| `port` | TCP 端口 | `5000` |
| `numAps` | Wi-Fi AP 数量 | `4` |
| `appSteadyRate` | 默认 steady 发送速率 | `50.9 Kbps` |
| `appBurstRate` | 默认 burst 发送速率 | `92.79 Mbps` |
| `appPacketSize` | 默认应用层包大小 | `1500 B` |
| `appTrafficModel` | 默认业务模型 | `duration` |
| `appInitialSendDelay` | connect 成功后再等多久才启动业务状态机 | `0 s` |
| `wifiAssocStaggerMs` | 同一个 AP 组内，STA 的 `WaitBeaconTimeout` 递增步长 | `3 ms` |
| `mptcpScheduler` | MPTCP 调度器 | `default` |
| `statsStart` | 稳态统计窗口起点 | `-1`，表示自动计算 |
| `statsStop` | 稳态统计窗口终点 | `-1`，表示自动计算 |

自动计算规则是：

- `statsStart = max(clientStart, simTime * 0.5)`
- `statsStop = simTime`

把默认值代入得到：

- `statsStart = max(2.0, 20.0 * 0.5) = 10.0 s`
- `statsStop = 20.0 s`

### 3.2 `flow-priority-30/avg-only` 的实际生效值

如果运行：

```bash
./run-myscript.sh --mode opt myscripts/pamptcp/pamptcp.cc -- \
  --trafficProfileDir=myscripts/pamptcp/flow-priority-30/avg-only
```

那么全局时序参数仍然沿用 `pamptcp.cc` 默认值，但业务参数会被 profile 覆盖：

| 项目 | 实际值 |
| --- | --- |
| client 总数 | `30` |
| 优先级 1 数量 | `6` |
| 优先级 2 数量 | `11` |
| 优先级 3 数量 | `13` |
| `appInitialSendDelay` | `0 s` |
| `appPacketSize` | `1400 B` |
| `p1 steady/burst rate` | `12 Kbps / 12 Kbps` |
| `p2 steady/burst rate` | `42 Kbps / 42 Kbps` |
| `p3 steady/burst rate` | `96 Kbps / 96 Kbps` |
| `appTrafficModel` | `duration` |
| `appSteadyTime` | `1.0 s` |
| `appBurstTime` | `0.0 s` |

这里要注意：

1. `avg-only` 场景虽然使用了 `duration` 模型，但 `steadyRate == burstRate`，所以“steady/burst 切换”不会改变发送速率。
2. `appBurstTime = 0.0 s` 在代码里会被夹成至少 `1 ns` 的状态切换延迟，但因为前后速率相同，对结果基本没有实际影响。

## 4. 关键概念

### 4.1 `clientStart` 不是“开始发 payload 的时间”

`clientStart` 只是 `RateDualModeApplication::StartApplication()` 被调度的基准时刻。到这个时刻后，app 会先创建 socket 并调用 `Connect()`。

真正开始发业务数据，至少还要经过：

1. `Connect()` 成功；
2. `appInitialSendDelay`；
3. 第一个发送间隔 `packetSize * 8 / currentRate`；
4. 实际 `socket->Send()` 成功。

所以：

- `clientStart` 是“应用启动时间”
- `ConnectionSucceeded` 是“连接建立完成时间”
- `firstPayloadTxTime` 是“第一个 payload 真正写入 socket 的时间”
- `payloadStartSeconds` 是“所有 client 中最早那个 `firstPayloadTxTime`”

### 4.2 `statsStart/statsStop` 统计的是“接收时间窗口”

`PriorityPacketSinkTracker` 和骨干口 `BackboneTcpPayloadTracker` 都是在接收回调里判断：

- 当前 `Simulator::Now()` 是否落在 `[statsStart, statsStop]`

所以这些统计窗口看的是：

- sink 端收到包的时间
- 或 server 骨干口 `MacRx` 收到包的时间

而不是 sender 侧开始发送的时间。

### 4.3 `wifiAssocStaggerMs` 的真实作用

这里的 Wi-Fi STA 设置了：

- `ActiveProbing = false`
- `WaitBeaconTimeout = 120 ms + j * wifiAssocStaggerMs`

这意味着 STA 不会主动发 probe request，而是先被动等 beacon。即使在 `t=0` 就已经收到了 beacon，STA 也要等自己的 `WaitBeaconTimeout` 到了，才会从候选 AP 列表里挑一个发送第一次 association request。

因此，`wifiAssocStaggerMs` 的作用不是“轻微扰动”这么简单，而是会直接拉开各个 STA 的首次关联请求时间。

## 5. 全局时间线

下面先给出不区分单个 UE 的全局事件时间。

### 5.1 `t = 0`

#### AP 初始 beacon

公式：

- `T_beacon(0) = 0`
- `T_beacon(k) = k * BeaconInterval`

本脚本没有改 `BeaconInterval`，因此沿用 `ApWifiMac` 默认值：

- `BeaconInterval = 102400 us = 102.4 ms`

代入后：

- 第 1 个 beacon：`0 ms`
- 第 2 个 beacon：`102.4 ms`
- 第 3 个 beacon：`204.8 ms`
- 第 4 个 beacon：`307.2 ms`

因为脚本显式设置了 `EnableBeaconJitter = false`，所以初始 beacon 不会随机抖动。

#### STA 开始扫描

所有 STA 在初始化时就开始扫描。由于 `ActiveProbing = false`，所以进入的是被动扫描状态 `WAIT_BEACON`。

### 5.2 `t = 0.40 s` 到 `0.768 s`

这是“路由基本准备好”的阶段。

#### server 与 AP 固定路由

- `t = 0.40 s`
  - server 加 `7.0.0.0/8` 到 PGW 的路由
  - 每个 AP 加自己 Wi-Fi 子网的直连路由
- `t = 0.41 + 0.01 * apIndex`
  - server 给每个 Wi-Fi 子网加路由
- `t = 0.41 s`
  - 每个 AP 加回 server `/32` 的骨干路由

#### 每个 UE 的策略路由

对第 `i` 个 UE：

- `base_i = 0.50 + 0.002 * i`
- NR 默认路由时间：`T_nr_route_i = base_i`
- Wi-Fi `ip rule` 时间：`T_rule_i = base_i + 0.01`
- Wi-Fi 子网路由时间：`T_wifi_subnet_route_i = base_i + 0.02`
- Wi-Fi table 2 默认路由时间：`T_wifi_default_route_i = base_i + 0.03`

因此可以把“第 `i` 个 UE 的策略路由完成时间”近似写成：

- `T_route_ready_i = 0.53 + 0.002 * i`

代入两种常见场景：

- 120-client 默认模式：最后一个 UE 是 `i = 119`
  - `T_route_ready_119 = 0.53 + 0.238 = 0.768 s`
- `avg-only` 场景：最后一个 UE 是 `i = 29`
  - `T_route_ready_29 = 0.53 + 0.058 = 0.588 s`

这说明在默认参数下，路由配置通常早于 `clientStart = 2.0 s` 完成。

### 5.3 `t = sinkStart`

公式：

- `T_sink_start = sinkStart`

默认值代入：

- `T_sink_start = 1.0 s`

这时 server 上 `PacketSink` 开始监听 TCP 端口。

### 5.4 RRC 快照时间

脚本显式打印三次 UE RRC 状态：

- `T_rrc_1 = 0.9 s`
- `T_rrc_2 = clientStart - 0.05 = 1.95 s`
- `T_rrc_3 = simTime - 0.05 = 19.95 s`

## 6. Wi-Fi 关联时间线

### 6.1 首次等待 beacon 的超时时间

对某个 AP 组内本地序号为 `j` 的 STA：

- `T_wait_beacon_j = 120 ms + j * wifiAssocStaggerMs`

默认值代入：

- `T_wait_beacon_j = 120 ms + 20j ms`

举例：

- `j = 0` 时，`120 ms`
- `j = 1` 时，`140 ms`
- `j = 2` 时，`160 ms`
- `j = 8` 时，`280 ms`
- `j = 29` 时，`700 ms`

### 6.2 首次 association request 的时间

在当前配置下，AP 从 `t = 0` 就开始发 beacon，且 beacon interval 是 `102.4 ms`。因此在没有异常丢失时，STA 很可能会在 `WaitBeaconTimeout` 触发前已经收到至少一个候选 AP 的 beacon。

于是首次关联请求时间可近似写成：

- `T_assoc_req_first_j ~= T_wait_beacon_j`

更准确地说：

- 如果在 `T_wait_beacon_j` 前候选 AP 列表非空，则
  - `T_assoc_req_first_j = T_wait_beacon_j`
- 否则会重新开始扫描，再延后一个扫描周期

### 6.3 两个典型场景里的时间范围

#### 120-client 默认模式

Wi-Fi 分组是：

- `ap1 = 30`
- `ap2 = 30`
- `ap3 = 30`
- `ap4 = 30`

所以每个 AP 组内本地序号 `j` 的范围是 `0..29`，首次关联请求时间大致分布在：

- `120 ms .. 700 ms`

#### `avg-only` 场景

`avg-only` 实际 `numClients = 30`，按当前行带划分逻辑，Wi-Fi 分组是：

- `ap1 = 9`
- `ap2 = 6`
- `ap3 = 9`
- `ap4 = 6`

因此各组的首次关联请求时间大致分布在：

- `ap1/ap3`: `120 ms .. 280 ms`
- `ap2/ap4`: `120 ms .. 220 ms`

这也解释了为什么在 `avg-only` 默认参数下，Wi-Fi 关联通常会明显早于 `clientStart = 2.0 s`。

## 7. 每个 client 的应用层时间线

下面把第 `i` 个 client 的时间线拆开。

### 7.1 app 启动时间

定义抖动：

- `J_i ~ U[0, clientStartJitter]`

则 app 启动时间是：

- `T_app_i = clientStart + J_i`

默认值代入：

- `J_i ~ U[0, 0.3 s]`
- `T_app_i = 2.0 + J_i`
- 所以 `T_app_i` 落在 `[2.0 s, 2.3 s]`

### 7.2 connect 开始与 connect 成功

`StartApplication()` 一启动就会调用 `Connect()`，因此：

- `T_connect_begin_i = T_app_i`

设 TCP/MPTCP connect 真正成功的耗时为 `C_i`，则：

- `T_connect_ok_i = T_app_i + C_i`

这里的 `C_i` 不是脚本显式固定的量，它取决于：

- NR 路径是否已可用
- Linux 路由是否已就绪
- MPTCP meta-socket 建立过程
- DCE/Linux 内核处理时延

### 7.3 业务状态机真正开始的时间

`ConnectionSucceeded()` 之后，代码不是立即发数据，而是再等 `appInitialSendDelay`：

- `T_traffic_start_i = T_connect_ok_i + appInitialSendDelay_i`

默认值代入：

- CLI 默认：`appInitialSendDelay = 0.2 s`
- `avg-only` 模板：也是 `0.2 s`

所以：

- `T_traffic_start_i = T_connect_ok_i + 0.2 s`

### 7.4 第一个发送事件被调度的时间

当前 app 不是“业务状态机一启动就立刻发第一包”，而是先算一个发送间隔：

- `Delta_i = appPacketSize_i * 8 / currentRate_i`
- `T_tx1_sched_i = T_traffic_start_i + Delta_i`

这一步很关键。它意味着：

- `appInitialSendDelay` 结束，不等于第一包已经发出
- 还要再等一个按速率计算出来的发送间隔

### 7.5 第一个 payload 真正发送成功的时间

设第一个发送事件触发后，第一次 `socket->Send()` 成功写入的时间为 `T_tx1_ok_i`，则：

- `T_tx1_ok_i >= T_tx1_sched_i`

如果 socket 没有阻塞、没有部分发送，那么常见情况下：

- `T_tx1_ok_i ~= T_tx1_sched_i`

代码里 `HasSentPayload()` / `GetFirstPayloadTxTime()` 记录的就是这个时间。

## 8. 默认值代入后的“首包时间”

### 8.1 如果不用 traffic profile，只看 CLI 默认业务参数

CLI 默认值：

- `appPacketSize = 1500 B`
- `steadyRate = 50.9 Kbps`
- `burstRate = 92.79 Mbps`
- `trafficModel = duration`
- 初始状态是 steady

因此首包调度间隔按 steady rate 计算：

- `Delta_cli = 1500 * 8 / 50900 ~= 0.235756 s`

代入得到：

- `T_tx1_sched_i = 2.0 + J_i + C_i + 0.2 + 0.235756`
- `T_tx1_sched_i = 2.435756 + J_i + C_i`

由于 `J_i in [0, 0.3]`，所以在“忽略 `C_i`”这个理想化下界下：

- 最早约 `2.435756 s`
- 最晚约 `2.735756 s`

### 8.2 `avg-only` 场景的首包时间

`avg-only` 的三种优先级速率不同，因此首包时间下界也不同。

#### 优先级 1

- `appPacketSize = 1400 B`
- `steadyRate = 12 Kbps`
- `Delta_p1 = 1400 * 8 / 12000 = 0.933333 s`

所以：

- `T_tx1_sched_p1,i = 2.0 + J_i + C_i + 0.2 + 0.933333`
- `T_tx1_sched_p1,i = 3.133333 + J_i + C_i`

#### 优先级 2

- `steadyRate = 42 Kbps`
- `Delta_p2 = 1400 * 8 / 42000 = 0.266667 s`

所以：

- `T_tx1_sched_p2,i = 2.466667 + J_i + C_i`

#### 优先级 3

- `steadyRate = 96 Kbps`
- `Delta_p3 = 1400 * 8 / 96000 = 0.116667 s`

所以：

- `T_tx1_sched_p3,i = 2.316667 + J_i + C_i`

### 8.3 `avg-only` 场景里最早可能开始发业务的是谁

由于：

- `p3` 的 steady rate 最大
- 初始状态就是 steady

因此在 `avg-only` 默认参数下，最早开始真实发 payload 的通常是 `priority = 3` 的流。

如果理想化地取：

- `J_i = 0`
- `C_i ~= 0`

那么整个场景理论上的最早首包下界约为：

- `2.316667 s`

实际运行时一般会稍晚一些，因为 `C_i` 不会严格等于 `0`。

## 9. `payloadStartSeconds`、`statsStart`、`statsStop` 的关系

这三个时间经常会被混淆。

### 9.1 `payloadStartSeconds`

定义：

- `payloadStartSeconds = min_i T_tx1_ok_i`

它表示：

- 所有 client 中，最早那个“真正成功发送 payload”的时间

默认情况下它通常会落在：

- `2.3 s` 之后
- `10.0 s` 之前

### 9.2 `statsStart` / `statsStop`

默认代入后：

- `statsStart = 10.0 s`
- `statsStop = 20.0 s`

所以默认统计窗口是：

- `[10.0 s, 20.0 s]`

这意味着：

1. 前面 `2.x s` 到 `10.0 s` 之间的大量启动期业务不会进入 `priority_metrics`。
2. 但这些早期业务仍然会计入 `PacketSink totalRxBytes`。

### 9.3 `PacketSink throughputMbps` 的分母

这里的分母不是 `simTime - sinkStart`，而是：

- `activeSeconds = simTime - payloadStartSeconds`

默认情况下：

- `activeSeconds = 20.0 - payloadStartSeconds`

如果某次运行 `payloadStartSeconds = 2.34 s`，则：

- `activeSeconds = 17.66 s`

## 10. 仿真结束附近的事件

### 10.1 `dumpSockets`

如果打开 `dumpSockets=1`，则：

- `dumpTime = max(clientStart + 1.0, simTime - 0.4)`

默认值代入：

- `dumpTime = max(3.0, 19.6) = 19.6 s`

### 10.2 accepted socket 快照

当前修复后的代码会在：

- `T_accept_snapshot = simTime - 1 ns`

读取 `PacketSink` 的 accepted socket 数量。

默认值代入：

- `T_accept_snapshot = 20.0 s - 1 ns`

### 10.3 app stop、sink stop、simulator stop

默认值代入：

- client app stop：`20.0 s`
- `PacketSink` stop：`20.0 s`
- `Simulator::Stop(...)`：`20.5 s`

## 11. 一页总结

如果只记住一条主线，可以记成下面这组表达式。

### 11.1 通用表达式

对第 `i` 个 client：

- `J_i ~ U[0, clientStartJitter]`
- `T_app_i = clientStart + J_i`
- `T_connect_ok_i = T_app_i + C_i`
- `T_traffic_start_i = T_connect_ok_i + appInitialSendDelay_i`
- `Delta_i = appPacketSize_i * 8 / steadyRate_i`
- `T_tx1_sched_i = T_traffic_start_i + Delta_i`
- `T_tx1_ok_i >= T_tx1_sched_i`

全局量：

- `payloadStartSeconds = min_i T_tx1_ok_i`
- `statsStart = max(clientStart, simTime * 0.5)`，若未显式指定
- `statsStop = simTime`，若未显式指定
- `PacketSink activeSeconds = simTime - payloadStartSeconds`

### 11.2 默认值代入后的简版

在 `avg-only` 默认运行下：

- `sinkStart = 1.0 s`
- `clientStart = 2.0 s`
- `J_i in [0, 0.3 s]`
- `appInitialSendDelay = 0.2 s`
- `stats window = [10.0 s, 20.0 s]`
- `Wi-Fi` 首轮关联请求大致在 `120 ms .. 280 ms` 或 `220 ms`
- `p1` 首包调度时间：`3.133333 + J_i + C_i`
- `p2` 首包调度时间：`2.466667 + J_i + C_i`
- `p3` 首包调度时间：`2.316667 + J_i + C_i`

因此：

1. `clientStart = 2.0 s` 不等于“开始发包”。
2. 默认稳态统计窗口从 `10.0 s` 才开始。
3. 在 `avg-only` 里最早发业务的一般是 `p3`，不是 `p1`。
4. `wifiAssocStaggerMs` 主要影响的是 Wi-Fi 首次关联请求时间，而不是 `clientStart`。
