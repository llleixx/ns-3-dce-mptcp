# 周期发送实验总结（2026-04-20）

## 1. 当前基线语义

### 1.1 发送语义

当前 `RateDualModeApplication` 已固定为如下语义：

- 不再使用 `PacketSize / PacketsPerBurst / SendInterval` 作为可配置发送节奏参数。
- 两种业务模式都统一为“**每 1 秒发送一次**”。
- 每次发送的数据量由当前状态决定：
  - steady 状态：发送 `appSteadyRate * 1s`
  - burst 状态：发送 `appBurstRate * 1s`
- 应用层直接构造这一整秒数据量对应的大 `Packet`，再交给 TCP/socket 自行分段和回压。

因此现在的实验里：

- `P1 steady @ 12 Kbps` 表示“每秒上报 `12 Kbps * 1s` 的报告”
- `P3 peak @ 25 Mbps` 表示“每秒上报 `25 Mbps * 1s` 的报告”

### 1.2 时延统计语义

当前 `priority_metrics` 已拆成两套口径：

- `delay_ms`
  - 只统计 **steady** 流量
  - peak 模板不计入这个时延与 SLA
- `overall_delay_ms`
  - 保留原始口径
  - 统计全部流量，包括 peak/report 流量

peak 的判断规则当前基于 `template_id` 是否包含 `peak`。

因此：

- `P1/P2 steady` 的低时延表现看 `delay_ms`
- `P3 peak` 这类大报告流量看 `overall_delay_ms`

## 2. 先验结论

### 2.1 P1 steady 本身没有问题

只保留 `P1 steady` 的场景：

- `p1-only-steady/default-stream1003-6s.json`

结果：

- `mean delay = 1.540 ms`
- `p95 = 3.486 ms`
- `SLA violation = 0`

说明：

- 当前 1 秒周期发送语义下，低速 steady 业务本身没有异常高时延。

### 2.2 单个 P1 peak 自身就会超过 20 ms SLA

只保留 `1 x P1 peak @ 20 Mbps` 的场景：

- `p1-only-1peak/default-stream1005-6s.json`

结果：

- `mean delay = 34.571 ms`
- `p95 = 38.289 ms`
- `SLA violation = 100%`

说明：

- 对 `P1 peak` 而言，当前“每秒一整份报告”的业务形状本身就会超过 `20 ms` 的低时延 SLA。
- 这不是其他流量竞争才能产生的问题。

### 2.3 统计里的 “activeFlows < totalFlows” 不等于某流没发送

在 `testprio + p3-peak` 里出现过：

- `P3 activeFlows = 12/13`

原因不是某个 `P3` 完全没发，而是：

- 服务器 `PacketSink` 只在**完整拼出一整条报告**时才记一次 `RxWithSeqTsSize`
- 某个 `P3` 连接在窗口 `[3s, 6s]` 内没有完成任何一整条报告的拼装
- 但 backbone payload 仍然已经收到了不少字节

因此：

- `activeFlows` 更接近“completed report flows”
- 不能直接解释成“调度器没给这个流任何资源”

### 4.5 p3-sub-peak 结论

这个场景非常支持如下判断：

> 把 `P1/P2` 更强地留在 NR，同时把 `P3 peak` 更强地推向 Wi-Fi，确实能显著改善 `P1/P2` steady 时延。

在当前内核中，现成的 `testprio` 已经验证了这件事：

- `P1/P2 -> NR`
- `P3 -> Wi-Fi`

并且在 `p3-sub-peak` 下它是表现最好的调度器。

## 5. 当前总判断

### 5.1 关于 p3-peak

如果场景中所有 `P3` 都是 peak/report：

- `blest` 仍然是最稳妥基线
- “强推 `P3 -> Wi-Fi`”会显著改善 `P1/P2`，但代价可能是 `P3` 吞吐下降或完成报告数下降

### 5.2 关于 p3-sub-peak

如果场景中 `P3` 只有一部分是 peak，另有 steady：

- `P1/P2 -> NR, P3 peak -> Wi-Fi` 这个方向是对的
- 现成的 `testprio` 已经在这个场景中跑赢 `default` 和 `blest`

### 5.3 关于 pablest

当前 `pablest` 版本在这两个场景下都不理想：

- `p3-peak` 下 steady-only 时延明显变差
- `p3-sub-peak` 下也没有体现出相对于 `blest` / `testprio` 的优势

## 6. 后续建议

如果要继续实现新算法，优先级建议如下：

1. 不要直接在 `p3-peak` 上“硬绑 `P3 -> Wi-Fi`”，因为 peak 全量上 Wi-Fi 很容易放大完成报告时延。
2. 更合理的方向是：
   - `P1/P2` 强偏 NR
   - `P3 peak` 偏 Wi-Fi
   - 但在 Wi-Fi backlog / service time 超预算时，允许 `P3` 回退 NR
3. 一个好的新算法应该是：
   - 在 `p3-sub-peak` 下接近 `testprio`
   - 在 `p3-peak` 下不要像 `testprio` 一样把 `P3` 吞吐和完成报告数拖坏

当前最值得作为设计起点的不是 `pablest`，而是：

- `testprio` 的“优先级到接入偏好”思想
- 加上一层 Wi-Fi 侧的软阈值回退
