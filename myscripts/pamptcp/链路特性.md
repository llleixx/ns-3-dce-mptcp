# Wi-Fi 与 NR 单链路特性实验记录

结论先说：本次已经完成 `Wi-Fi only` 和 `NR only` 两类单链路实验，每次只让 TCP 流走一个接入链路，设备数量为 `1, 4, 8, 15, 30`。统计窗口保持为 10s 仿真、4s 开始统计、10s 停止统计、客户端启动抖动 1s；输出 JSON 中的 `delay_ms` 是应用层完成时间，也就是每个带时间戳 TCP 突发从发送端生成到接收端完整收到的时间。Wi-Fi 的低负载应用层完成时间约 `0.57ms`；NR 的 `64B` 点出现约 `17ms` 的孤立异常，补跑 `32, 128, 256, 512, 1024, 2048B` 后均约 `3.25ms`，因此 NR 小突发低延迟应参考 `1024B` 附近，而不是把 `64B` 当成链路最低时延。最终建议保留 Wi-Fi 梯度 `64, 1024, 16384, 65536, 262144, 1048576, 2097152, 4194304 B/s/UE`，NR 梯度 `64, 1024, 16384, 65536, 262144, 524288, 1048576, 2097152 B/s/UE`，其中 NR 的 `64B` 只作为异常控制点保留。

## 实验设置

路径模式：

- `wifi-only`：客户端 socket 绑定 Wi-Fi 地址，只走 Wi-Fi 接入链路；MPTCP 自动禁用，用普通 TCP 隔离单链路。
- `nr-only`：客户端 socket 绑定 NR UE 地址，只走 5G NR 接入链路；同样禁用 MPTCP。

关键参数：

| 参数 | 取值 | 含义 |
|---|---:|---|
| `numAps` | 1 | 只放 1 个 Wi-Fi AP，和后续 MPTCP 实验保持一致 |
| `simTime` | 10s | 仿真到 10 秒停止 |
| `statsStart` / `statsStop` | 4s / 10s | 只统计稳定窗口，避开连接建立和启动抖动 |
| `clientStartJitter` | 1s | 客户端启动时间在 1 秒内随机错开，避免完全同步启动 |
| 设备数量 | 1, 4, 8, 15, 30 | 覆盖单用户、小规模、中等和 30 设备场景 |
| `bytes/burst` | B/s/UE | 每个 UE 每秒产生一次应用层 TCP 突发，大小等于该字节数 |

`bytes/burst` 不是 IP 包大小，而是 `RateDualModeApplication` 每秒生成的应用层字节数。因为发送端启用了 `SeqTsSizeHeader`，接收端 `PacketSink` 会等一个 TCP 应用突发完整重组后才记录一次 `RxWithSeqTsSize`，所以 JSON 里的 `priority_metrics.entries[scope=overall].delay_ms` 近似代表“这次突发完成用了多久”。

`offered_mbps = clients * bytes_per_burst * 8 / 1e6`，单位是 Mbps。`rx_mbps` 是统计窗口内接收端实际收到的应用层吞吐。两者接近表示链路能消化负载；`rx_mbps` 明显低于 offered 且时延暴涨，说明进入重载/排队区。

注意：NR 的 `64B` 点不是最低时延点，结果约 `17ms`，而 `1024B` 点约 `3.3ms`。为排除单点误判，额外补跑了 1 UE 的 `32, 64, 128, 256, 512, 1024, 2048B`：除 `64B` 外，其余点均约 `3.25ms`。因此 `64B` 更像 `SeqTsSizeHeader + Linux TCP + NR` 组合下触发的特殊边界，而不是 NR 链路的真实低负载基线；后续如果要专门研究“ping 类极小负载”，应使用专门的 ICMP/UDP 小包脚本或至少避开只看这个 `64B` TCP 应用突发点。

## 梯度收敛

最终保留的梯度如下：

- Wi-Fi：`64, 1024, 16384, 65536, 262144, 1048576, 2097152, 4194304 B/s/UE`
- NR：`64, 1024, 16384, 65536, 262144, 524288, 1048576, 2097152 B/s/UE`

Wi-Fi 的单链路容量更高，30 UE 下 `2MiB/UE/s` 仍能达到约 `500.5Mbps` 且 p95 约 `60.8ms`，`4MiB/UE/s` 才明显进入高排队时延区。NR 在 30 UE 下 `1MiB/UE/s` 已经 p95 到 `128.5ms`，`2MiB/UE/s` 吞吐只能到 `377.5Mbps`，p95 到 `2784.2ms`，这是明确的重载点。因此 NR 梯度上界不再继续扩大，Wi-Fi 梯度保留更大的 `4MiB` 上界。

## 对后续 MPTCP 调度实验的启示

MPTCP（Multipath TCP，多路径 TCP）调度实验里，Wi-Fi 和 NR 不应使用同一个“每 UE 负载”直觉。Wi-Fi 在本拓扑下更像高容量、低基础时延链路；NR 的基础调度时延更高，且 15 到 30 UE 时更早进入排队区。

如果要构造“中等压力但未崩溃”的混合场景，可以优先参考：

- Wi-Fi 单链路：30 UE、`1MiB` 或 `2MiB` 每秒突发。
- NR 单链路：30 UE、`512KiB` 或 `1MiB` 每秒突发。

如果要观察调度算法在极端拥塞下的选择，可以使用：

- Wi-Fi：30 UE、`4MiB` 每秒突发。
- NR：30 UE、`2MiB` 每秒突发。

这些结论只对应当前脚本里的无线参数：Wi-Fi 802.11ax 5GHz、160MHz、1 AP；NR 4.9GHz、100MHz、numerology 2、TDD pattern `DL|F|UL|UL|UL|`、UL fixed MCS 25。修改带宽、MCS、TDD 配置、AP 数量或设备位置后，应重新跑同一套脚本。

## 如何比较 Wi-Fi 与 NR 的多设备调度能力

如果目标不是“谁的单链路峰值更高”，而是“谁在多 UE 场景下更会调度资源”，实验不能只看单设备容量。更合理的做法是先估计每条链路在不同 UE 数下的容量，再用相对容量归一化负载去比较吞吐、时延和公平性。

这里的调度能力指：当多个 UE（User Equipment，用户设备）同时发送时，链路能否把无线资源稳定、公平、低时延地分给这些 UE。Wi-Fi 里资源分配受 CSMA/CA（Carrier Sense Multiple Access with Collision Avoidance，带冲突避免的载波侦听多址接入）、聚合、重传和 AP 行为影响；NR 里资源分配主要由 gNB（gNodeB，5G 基站）的 MAC scheduler（Medium Access Control scheduler，媒体接入控制层调度器）按时隙分配。

### 第一步：容量探测

对 `wifi-only` 和 `nr-only` 分别运行，UE 数仍取：

```text
N = 1, 4, 8, 15, 30
```

对每个 N 逐步增加 `bytes/burst`，记录 offered load 与接收端吞吐。定义两个容量：

```text
C_1 = 单 UE 时可达到的容量
C_N = N 个 UE 同时发送时可达到的总容量
```

`C_N` 不应简单假设为 `C_1`，因为多 UE 时会出现调度开销、竞争开销、控制信令开销、重传和排队。现有 `final-grid` 数据已经能粗略观察容量区间，但如果要更精确，可以在接近拐点的位置继续加中间点，或做二分搜索。

建议同时定义一个“可用容量”而不只看最大吞吐：

```text
usable_C_N = 满足 throughput_efficiency >= 0.95 且 p95_delay_ms <= 100ms 的最大 rx_mbps
```

其中 `throughput_efficiency = rx_mbps / offered_mbps`。最大吞吐适合看物理上限，可用容量更适合后续 MPTCP 业务负载设计。

### 第二步：归一化压力实验

为了公平比较 Wi-Fi 和 NR，不建议直接给两条链路相同的 Mbps 负载。因为 Wi-Fi 和 NR 当前配置下容量不同，固定 Mbps 会让一条链路处在轻载、另一条处在重载。

建议按相对容量设置每 UE 负载：

```text
per_ue_load = alpha * usable_C_N / N
```

其中 `alpha` 表示压力系数：

```text
alpha = 0.25, 0.50, 0.75, 1.00, 1.25
```

含义如下：

| `alpha` | 含义 | 预期现象 |
|---:|---|---|
| 0.25 | 轻载 | 吞吐应接近 offered，时延主要反映基础链路与调度周期 |
| 0.50 | 中低负载 | 应基本无排队，可观察多 UE 调度开销 |
| 0.75 | 中高负载 | 开始接近链路可用容量，p95/p99 更有区分度 |
| 1.00 | 接近可用容量 | 调度能力差异会明显体现为时延和公平性差异 |
| 1.25 | 过载 | 观察谁先出现吞吐效率下降、排队爆炸或 UE 饥饿 |

这一步的核心是：让 Wi-Fi 和 NR 都处在“各自容量的同等压力比例”下，然后比较表现。

### 应对比的指标

第一类是吞吐能力：

```text
throughput_efficiency = rx_mbps / offered_mbps
scaling_efficiency = C_N / C_1
per_ue_goodput = rx_mbps / N
```

`throughput_efficiency` 看链路是否吃下负载；`scaling_efficiency` 看 UE 数增加后总容量保持得怎样；`per_ue_goodput` 看平均每个 UE 实际拿到多少应用层吞吐。

第二类是时延能力：

```text
delay_mean_ms
delay_p50_ms
delay_p95_ms
delay_p99_ms
delay_max_ms
```

平均值只能说明总体水平，`p95/p99/max` 更能反映调度尾部问题。调度能力强的链路，在 `alpha` 接近 1 时不应出现很快的 p95/p99 爆炸。

第三类是公平性：

```text
min_flow_throughput_mbps
max_flow_throughput_mbps
flow_spread = max_flow_throughput_mbps / min_flow_throughput_mbps
Jain fairness index = (sum(x_i)^2) / (N * sum(x_i^2))
```

`x_i` 是第 i 个 UE 的吞吐。Jain fairness index（Jain 公平指数）取值范围是 `(0, 1]`，越接近 1 表示越公平。现有 JSON 已经有 `min_flow_throughput_mbps` 和 `max_flow_throughput_mbps`，可以粗略判断是否有 UE 明显落后；但还没有导出所有 UE 的 `x_i`，所以暂时不能严格计算 Jain 指数。若要把公平性作为核心结论，需要给 `link-characteristics-report` 增加 per-UE 吞吐数组输出。

第四类是服务完整性：

```text
active_flows / expected_flows
delay_active_flows / expected_flows
client_connect.connected / client_connect.total
```

这些指标用于排除“总吞吐看起来不错，但部分 UE 没被正常服务”的情况。如果 30 UE 里有 UE 没有 delay sample，或者连接没建立，这个点不能当作公平调度成功。

### 判定标准

在同一组 `N` 和同一组 `alpha` 下，可以按下面顺序判断：

1. 先看 `client_connect.connected == total` 和 `active_flows == expected_flows`，否则该点无效或需要单独解释。
2. 再看 `throughput_efficiency`，谁更接近 1，谁更能消化当前压力。
3. 再看 `delay_p95_ms` 和 `delay_p99_ms`，谁的尾部时延更低，谁的调度更稳定。
4. 再看公平性，谁的 `flow_spread` 更小、Jain 指数更接近 1，谁更少让个别 UE 饥饿。
5. 最后看 `scaling_efficiency`，谁从 1 UE 到 30 UE 的容量保持更好，谁的多设备扩展能力更强。

最终结论不要写成“Wi-Fi 一定比 NR 强”或“NR 一定比 Wi-Fi 强”，而应按负载区间表达。例如：

- 轻载下：比较基础时延和调度周期。
- 中载下：比较吞吐效率与 p95 时延。
- 接近容量时：比较 p99/max 时延和公平性。
- 过载时：比较谁先出现吞吐效率下降和 UE 饥饿。

### 当前脚本还需要补的输出

现有 JSON 足够支持：

- 总吞吐 `rx_mbps`
- offered/received 吞吐效率
- overall delay mean/p50/p95/p99/max
- active flow 数
- min/max flow throughput

如果要严谨回答“谁的调度公平性更强”，建议再补：

- 每个 UE 的 `rx_bytes`
- 每个 UE 的 `throughput_mbps`
- 每个 UE 的 delay mean/p95/p99
- Jain fairness index

这些数据源已经在 `PriorityPacketSinkTracker::m_clientStats` 中按 client 保存，当前只是没有写进 JSON。实现上可以在 `PriorityMetricsReport` 里增加 `per_client_entries`，由 `BuildSummary()` 输出每个 client 的吞吐和时延分布，再由 `summarize-link-characteristics.py` 计算 Jain 指数与 per-UE tail latency。
