# Wi-Fi 与 NR 链路调度能力容量探测报告

结论先说：本次补做了面向“链路调度能力”的容量探测，不再直接把 `链路特性.md` 里的单点吞吐当作容量上限，而是先探出单设备容量 `C_1` 和多设备总容量 `C_N`，再比较 `C_N / C_1`。在当前参数下，Wi-Fi 的绝对容量更高，`C_1` 约 `1923.7 Mbps`，`C_30` 约 `739.0 Mbps`；NR 的绝对容量较低，`C_1` 约 `394.8 Mbps`，`C_30` 约 `373.7 Mbps`。但如果看调度能力保持率 `C_N / C_1`，NR 明显更强：30 UE 时仍保持 `0.947`，Wi-Fi 30 STA 时只剩 `0.384`。因此结论应写成：Wi-Fi 是高单链路容量但多 STA 竞争扩展性差；NR 是低单链路容量但多 UE 调度保持能力强。

## 为什么需要重新做容量探测

原来的 `myscripts/pamptcp/链路特性.md` 主要回答的是：在 `RateDualModeApplication` 每秒生成一个 TCP 应用突发的业务模型下，Wi-Fi 与 NR 的应用层完成时间和吞吐表现如何。这个实验对后续 MPTCP（Multipath TCP，多路径 TCP）业务设计很有用，但不能直接回答“链路调度能力”。

原因是 `RateDualModeApplication` 的发送方式是每秒生成一个较大的应用单元，再经 Linux TCP 发送。高负载时，JSON 里的 `priority_metrics.throughput_mbps` 只统计在窗口内完整收到的应用单元，容易受到“应用单元是否跨过统计窗口”的影响。它适合看应用层完成时间和业务体验，但不适合精确探无线容量平台。

所以本次对“调度能力”的比较改为两步：

1. 先对每条链路做 offered-load 容量探测，找出单设备容量 `C_1` 和 N 设备并发总容量 `C_N`。
2. 再用 `C_N / C_1` 衡量多设备场景下容量保持能力，也就是调度/竞争机制在多用户时还能保留多少单用户能力。

## 核心定义

### C_1

`C_1` 表示一条链路在 `1` 个发送端独占接入时可达到的总吞吐平台，单位是 `Mbps`。

本报告里：

```text
C_1 = N = 1 时，在持续增加 offered load 后测得的最大稳定总吞吐
```

例如 Wi-Fi 单 STA 从 `200 Mbps` 一直加到 `4000 Mbps` offered load，吞吐在 `2000 Mbps` offered load 之后稳定在约 `1923.7 Mbps`，所以取：

```text
Wi-Fi C_1 = 1923.7 Mbps
```

NR 单 UE 从 `100 Mbps` 加到 `600 Mbps` offered load，吞吐在 `400 Mbps` 附近进入平台，之后继续加 offered load 主要增加排队时延，吞吐维持在约 `394.8 Mbps`，所以取：

```text
NR C_1 = 394.8 Mbps
```

### C_N

`C_N` 表示 `N` 个设备同时发送时，这条链路整体可达到的总吞吐平台，单位同样是 `Mbps`。

本报告里：

```text
C_N = N 个发送端并发时，在持续增加每设备 offered load 后测得的最大稳定总吞吐
```

注意 `C_N` 是总吞吐，不是每设备吞吐。例如：

```text
Wi-Fi C_30 = 739.0 Mbps
```

表示 30 个 Wi-Fi STA 同时上行时，整个 Wi-Fi 接入链路总吞吐平台约为 `739.0 Mbps`，不是每台 `739.0 Mbps`。

### C_N / C_1

`C_N / C_1` 是本报告用于比较“多设备调度能力”的核心指标。

```text
C_N / C_1 = N 设备总容量 / 单设备容量
```

它衡量的是：设备数量从 1 增加到 N 后，链路还能保持多少单设备容量。

如果 `C_N / C_1` 接近 `1`，说明多设备并发并没有明显损失总容量，调度/资源分配能力强。如果明显小于 `1`，说明多设备竞争、控制开销、碰撞、重传、排队或公平性问题导致总容量损失明显。

### offered load

`offered load` 指应用层主动注入网络的发送负载，单位是 `Mbps`。

本次扫描用 `offeredLoadMbpsPerClient` 表示每个设备的 offered load：

```text
总 offered load = N * offeredLoadMbpsPerClient
```

例如 Wi-Fi `N=30`、`offeredLoadMbpsPerClient=40` 时：

```text
总 offered load = 30 * 40 = 1200 Mbps
```

### gross throughput 与 net throughput

Wi-Fi 的 `link-info-wifi-only` 输出两套吞吐：

- `grossThroughputMbps`：包含 `SeqTsSizeHeader` 的应用层包吞吐，不包含 UDP/IP/MAC/PHY 头。
- `netPayloadThroughputMbps`：去掉 `SeqTsSizeHeader` 后的净应用层 payload 吞吐。

NR 的 `link-info-nr-only` 原始输出是净 payload 吞吐。本报告为了让 Wi-Fi 与 NR 的 offered load 口径一致，把 NR 的净吞吐按 `packetSize=1400B`、`SeqTsSizeHeader=20B` 换算成 gross 口径：

```text
NR gross throughput = NR net throughput * 1400 / 1380
```

最终容量表统一使用 `gross_mbps`。

### throughput efficiency

`throughput efficiency` 表示实际吞吐占 offered load 的比例：

```text
eff = gross_mbps / offered_total
```

如果 `eff` 接近 `1`，说明链路基本消化了 offered load。如果 `eff` 明显下降，而吞吐不再增长，说明已经进入容量平台或过载区。

### flow spread

`flow spread` 用来粗略观察公平性：

```text
flow spread = max_flow_throughput / min_flow_throughput
```

数值越接近 `1`，说明不同设备拿到的吞吐越均匀。它不是严格的 Jain 公平指数（Jain fairness index），但足够粗略判断是否出现明显饥饿。

## 实验工具与拓扑

本次最终容量探测使用已有的两个连续 offered-load 脚本：

- `myscripts/120-demo/link-info/wifi-only/link-info-wifi-only.cc`
- `myscripts/120-demo/link-info/nr-only/link-info-nr-only.cc`

这两个脚本使用 `OnOffApplication + UDP` 连续发小包，应用层包大小为 `1400 B`，并启用 `SeqTsSizeHeader` 统计应用层时延。选择它们而不是 `RateDualModeApplication + TCP` 的原因是：容量探测更关心无线接入链路在连续负载下的吞吐平台，小包连续发送比每秒一个超大 TCP 应用突发更容易稳定扫出容量拐点。

### 控制变量

两条链路都使用同一组设备数量：

```text
N = 1, 4, 8, 15, 30
```

每个 `N` 下逐步提高每设备 offered load，直到总吞吐进入平台，或者继续加负载只增加时延/丢包/不公平性。

### Wi-Fi 关键参数

| 参数 | 取值 | 含义与影响 |
|---|---:|---|
| 标准 | 802.11ax 5GHz | Wi-Fi 6，决定 PHY/MAC 能力 |
| 信道宽度 | 160 MHz | 越宽理论 PHY 速率越高 |
| 频点 | 5250 MHz | 5GHz 频段 |
| AP/STA 天线 | AP 4x4，STA 2x2 | 影响 MIMO 空间流能力 |
| `numAps` | 1 | 所有 STA 共享一个 AP |
| `wifiEnableOfdma` | false | 显式关闭 OFDMA，以匹配 `链路特性.md` 的默认 Wi-Fi 参数 |
| `wifiEnableUlOfdma` | false | 关闭上行 OFDMA |
| `wifiEnableBsrp` | false | 关闭 BSRP |
| AP-server backbone | 10Gbps / 0.5ms | 有线回传不是瓶颈 |

这里的 OFDMA（Orthogonal Frequency Division Multiple Access，正交频分多址）是 Wi-Fi 6 的多用户调度能力。关闭 OFDMA 后，多 STA 上行主要受 CSMA/CA（Carrier Sense Multiple Access with Collision Avoidance，带冲突避免的载波侦听多址接入）、聚合、重传和排队影响。

### NR 关键参数

| 参数 | 取值 | 含义与影响 |
|---|---:|---|
| 载频 | 4.9 GHz | NR 工作频段 |
| 带宽 | 100 MHz | 决定可调度频域资源 |
| numerology | 2 | 子载波间隔为 60 kHz，影响 slot 时长和调度周期 |
| TDD pattern | `DL|F|UL|UL|UL|` | 时分双工模式，偏上行 |
| UL MCS | fixed 25 | 上行固定调制编码等级，越高理论速率越高但对信道要求更高 |
| UE/gNB 天线 | UE 1x2，gNB 2x2 | 影响链路能力 |
| gNB scheduler | `NrMacSchedulerOfdmaRR` | NR MAC 层 OFDMA round-robin 调度 |
| PGW-server backbone | 10Gbps / 0.5ms | 有线回传不是瓶颈 |

NR（New Radio，5G 新空口）中，UE（User Equipment，用户设备）上行资源由 gNB（gNodeB，5G 基站）的 MAC scheduler（Medium Access Control scheduler，媒体接入控制层调度器）按时隙和频域资源块分配。因此 NR 的多 UE 容量保持能力主要体现的是 gNB 调度器能否稳定、公平地把同一小区资源分给多个 UE。

| Wi-Fi | 4 | 1553.8 | 600 | 0.647 | 269.3 | 1.26 | 0.808 |
| Wi-Fi | 8 | 1297.4 | 250 | 0.649 | 564.1 | 1.50 | 0.674 |
| Wi-Fi | 15 | 1047.1 | 160 | 0.436 | 1137.6 | 1.74 | 0.544 |

### 可用容量

为了避免只看峰值吞吐导致误解，本报告额外列出一个“可用容量”参考点：

```text
可用容量 = 满足 eff >= 0.95 且平均时延 <= 100ms 的最高吞吐点
```

这个定义不是物理容量，而是低排队、低损耗、高效率的工作区间参考。

| Wi-Fi | 4 | 1523.0 | 400 | 0.952 | 94.2 | 1.11 |
| Wi-Fi | 8 | 1169.4 | 150 | 0.974 | 99.3 | 1.06 |
| Wi-Fi | 15 | 573.4 | 40 | 0.956 | 78.2 | 1.13 |
| Wi-Fi | 30 | 无满足点 | - | - | - | - |
| NR | 1 | 394.8 | 400 | 0.987 | 41.5 | 1.00 |

## 结果分析

### 1. Wi-Fi：绝对容量高，但 C_N / C_1 随设备数快速下降

Wi-Fi 单 STA 容量约为：

```text
C_1 = 1923.7 Mbps
```

但随着 STA 数增加，总容量不是保持不变，而是持续下降：

```text
C_4  = 1553.8 Mbps, C_4/C_1  = 0.808
C_8  = 1297.4 Mbps, C_8/C_1  = 0.674
C_15 = 1047.1 Mbps, C_15/C_1 = 0.544
C_30 = 739.0 Mbps,  C_30/C_1 = 0.384
```

这说明在关闭 Wi-Fi OFDMA 的当前配置下，多 STA 并发会显著损失总容量。主要可能原因包括：

- 多 STA 上行共享同一个 AP 和同一个信道。
- CSMA/CA 竞争导致退避、空口争用和碰撞避免开销增加。
- 高负载下队列堆积、重传和不同 STA 之间的发送机会差异增大。
- 从 `flow spread` 看，Wi-Fi 从 8 STA 起公平性开始明显变差，30 STA 平台点 spread 到 `2.91`。

因此 Wi-Fi 更像“单链路能力很强，但多用户竞争代价大”的链路。

### 2. NR：绝对容量低，但 C_N / C_1 几乎保持

NR 单 UE 容量约为：

```text
C_1 = 394.8 Mbps
```

多 UE 时，总容量基本保持在同一量级：

```text
C_4  = 397.5 Mbps, C_4/C_1  = 1.007
C_8  = 394.5 Mbps, C_8/C_1  = 0.999
C_15 = 388.1 Mbps, C_15/C_1 = 0.983
C_30 = 373.7 Mbps, C_30/C_1 = 0.947
```

这说明 NR 的小区总上行容量主要由 gNB 侧资源池决定，多个 UE 是共享同一个容量池，而不是把容量叠加。虽然 NR 的 `C_1` 远低于 Wi-Fi，但从 `C_N / C_1` 看，NR 的多 UE 调度保持能力很强。

NR 的 `flow spread` 也较稳定：

```text
N=4:  1.03
N=8:  1.08
N=15: 1.12
N=30: 1.31
```

这说明当前 `NrMacSchedulerOfdmaRR` 调度器在多 UE 上行时能比较均匀地分配资源，没有出现 Wi-Fi 那样明显的多用户容量塌缩。

### 3. 绝对容量与调度能力不能混为一谈

如果问“谁吞吐更高”，答案是 Wi-Fi：

```text
Wi-Fi C_1  = 1923.7 Mbps, NR C_1  = 394.8 Mbps
Wi-Fi C_30 = 739.0 Mbps,  NR C_30 = 373.7 Mbps
```

即使到 30 设备，Wi-Fi 的峰值总吞吐仍大约是 NR 的 `1.98` 倍。

但如果问“谁的多设备调度能力更强”，应看 `C_N / C_1`：

```text
Wi-Fi C_30/C_1 = 0.384
NR C_30/C_1    = 0.947
```

这个指标下 NR 明显更强，因为它在 30 UE 并发时仍保留了约 `94.7%` 的单 UE 容量，而 Wi-Fi 只保留约 `38.4%`。

## 对 MPTCP 调度实验的启示

MPTCP 调度算法不能只根据“Wi-Fi 峰值更高”就把高并发业务都压到 Wi-Fi。更合理的理解是：

- Wi-Fi：适合承担高吞吐业务，但多 STA 高并发时竞争开销和公平性问题明显。
- NR：适合提供稳定的多 UE 资源分配，绝对容量较低，但容量保持率和公平性更好。
- 30 设备场景下，Wi-Fi 的可用低时延工作点比峰值容量低得多；NR 在 `351 Mbps` 左右仍能保持低时延和高效率。

因此后续 MPTCP 调度算法如果要同时考虑吞吐和尾时延，可以把 Wi-Fi 当作高容量但高并发敏感链路，把 NR 当作容量较小但调度稳定链路。

## 结论

本次容量探测得到的关键结论如下：

1. Wi-Fi 的绝对容量明显高于 NR：`C_1` 约 `1923.7 Mbps`，`C_30` 约 `739.0 Mbps`。
2. NR 的绝对容量较低：`C_1` 约 `394.8 Mbps`，`C_30` 约 `373.7 Mbps`。
3. 但从 `C_N / C_1` 看，NR 多 UE 调度保持能力明显强于 Wi-Fi。
4. Wi-Fi 的 `C_N / C_1` 从 `N=4` 的 `0.808` 下降到 `N=30` 的 `0.384`，说明多 STA 竞争导致容量保持率显著下降。
5. NR 的 `C_N / C_1` 从 `N=4` 到 `N=30` 基本维持在 `0.947-1.007`，说明当前 NR 调度器能较好保持小区总容量。

最终表述建议：

```text
Wi-Fi 是高绝对容量、低多用户保持率链路；
NR 是低绝对容量、高多用户保持率链路。
如果评价“调度能力”，NR 更强；
如果评价“峰值吞吐”，Wi-Fi 更强。
```

## 局限性

本报告的容量 `C_N` 使用 UDP 连续小包 offered-load 扫描，目的是隔离无线接入链路调度能力。它不等同于 `RateDualModeApplication + Linux TCP` 下的业务完成时间，也不直接代表 MPTCP 应用层最终体验。

具体局限包括：

- UDP 不包含 TCP 拥塞控制、发送缓冲、重传和接收窗口影响。
- 平台点平均时延可能已经很高，因此 `C_N` 是容量上限，不是推荐工作点。
- Wi-Fi 明确关闭 OFDMA，以匹配当前 `链路特性.md` 的默认参数；如果开启 OFDMA，Wi-Fi 多用户保持率可能变化。
- 修改带宽、MCS、TDD pattern、AP 数量、天线配置、设备位置后，应重新探测 `C_1` 和 `C_N`。
